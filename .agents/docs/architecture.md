# Architecture

What Coral is built out of, where each part lives, how the parts fit together, and the rules that hold across all of it.

Parts that do not exist yet are described here as what they will be. "The Codebase" below marks which those are, and is the only place they are marked.

Each section is prose about that part of the system, followed by the rules that part has to keep. Every limit quoted here that is a real platform limit says so. Numbers that were chosen rather than measured say so where they appear, and are collected at the end.

## The Platform

Coral is a GitHub Actions workflow. There is no cloud account, no infrastructure to provision, and no service standing by between reviews. GitHub supplies the trigger, the compute, the checkout, and the credential, and Coral supplies the review.

Coral is written in Python and built with `uv`. The review agent is built with DeepAgents. Models are reached through OpenRouter, using the `langchain-openrouter` package and its `ChatOpenRouter` chat model, and no model provider is called directly. The model is `~deepseek/deepseek-v4-flash-latest`. It offers a 1,048,576-token context window and supports tool calling, structured outputs, and a reasoning effort setting, which are the capabilities the rest of this document depends on. The leading tilde is an OpenRouter alias resolving to the newest release in the DeepSeek V4 Flash family, so the model behind it changes without notice.

- Coral owns no datastore. Everything Coral needs to remember about a pull request is already written on that pull request, and Coral reads it back at the start of every run. This is the decision the rest of the design hangs off. The marker on every comment Coral posts is what makes it possible, and reading past findings before making new ones is what spends it.
- Dependencies are managed against a committed lockfile and installed on the runner with `uv sync --frozen`. Nothing resolves versions at run time.
- The interpreter version and the three checks — `ruff` for lint and format, `pytest` for tests, and `mypy` for type checking — are configured in `.python-version` and `pyproject.toml` and nowhere else. `.agents/docs/code-style.md` says what each is set to, and `.agents/docs/development.md` names the command that runs it.

## Installation And Packaging

Coral ships as composite actions in its own repository, wired together by a reusable workflow, and installed by a short file in each repository that calls that workflow. What drifts between repositories is therefore a tag plus a small block of boilerplate, and the boilerplate is worth keeping identical.

There is no way to skip the per-repository file. An Enterprise Cloud organization can push a workflow across its repositories through a ruleset, but a ruleset workflow runs only on `pull_request`, `pull_request_target`, and `merge_group`, so it could never carry the comment triggers. It is also a merge gate rather than a trigger, which would make a Coral outage block merges across the organization and would contradict Coral's review being advisory.

- The per-repository file carries five things, and it has to carry all five: the version pin, the OpenRouter secret, the `on:` block naming the events, the `permissions:` block, and the concurrency group. A reusable workflow cannot declare its caller's triggers and cannot grant itself permissions the caller withheld, so those three cannot move upstream.
- Coral's own repository is public, so any calling repository reaches the reusable workflow with nothing configured on either side. Publishing from a private repository would instead depend on an organization access setting and would be unreachable from a public caller.
- Coral needs one secret: an OpenRouter API key, supplied to the reusable workflow by the repository that calls it. The GitHub token comes from the job, so there is nothing else to store.

## The Codebase

Coral is one command-line program with three subcommands: `coral resolve`, `coral review`, and `coral report`. They are one console script over one package, and each composite action's `run:` step invokes one of them. Of the run's five steps, three are these subcommands; the checkout is GitHub's own action and the setup step is shell. What all three subcommands need — reading the event payload, writing step outputs, finding the runner's temporary directory — therefore has one home rather than three.

This is the whole layout, and every part of it that does not exist yet is marked.

- `coral/cli.py` — the console script. One `argparse` parser, three subcommands, and nothing else.
- `coral/runner.py` — what every subcommand needs from the Actions runner: the event, step outputs, the temporary directory, and the one reading of `GITHUB_WORKSPACE`.
- `coral/resolve.py` — the gatekeeper step: fetch the pull request and the conversation, acknowledge the request, decide whether to go on. The only gate it applies so far is the closed pull request.
- `coral/review.py` — the review step: build the agent, run it, post the result. The review is hardcoded until the agent exists.
- `coral/report.py` — the failure step, which runs on the job's failure path. Not built.
- `coral/agent.py` — the only module that imports `deepagents`. Not built.
- `coral/schema.py` — the review object and its anchors: the contract with the agent, and the only place structure originates.
- `coral/command.py` — recognizing `/coral` in a comment body. Not built.
- `coral/environment.py` — building the environment the agent's shell gets. Not built.
- `coral/deadline.py` — the four parts of the time budget. Not built.
- `coral/diff.py` — the merge-base diff. Anchor validation is not built.
- `coral/github/client.py` — the one authenticated transport.
- `coral/github/conversation.py` — the GraphQL query, the bound, and the file the conversation crosses the step boundary on.
- `coral/github/marker.py` — the sentinel: writing it and reading it back.
- `coral/github/reactions.py` — the two reaction namespaces.
- `coral/github/post.py` — creating the review and demoting anchors. The retry on a rejection is not built.
- `coral/prompts/review.md` — what Coral looks for. Not built.
- `tests/` — one `test_<module>.py` per module under test.
- `.github/workflows/coral.yml` — the `workflow_call` workflow.
- `actions/setup/` — installs `uv` and builds Coral's own virtual environment.
- `actions/resolve/` and `actions/review/` — one `run:` step each, invoking the console script.
- `examples/coral.yml` — the file a repository copies in to install Coral.

The rules this layout keeps:

- `coral/agent.py` is the only module that imports `deepagents`. It builds the model client, builds the backend, builds the agent, runs it, and hands back the review object. Every other module depends on that object's schema and never on the framework, so there is no second place a framework type can reach into Coral's own code. The cost is that the framework symbol is the only test seam: a test that wants to exercise anything downstream of the agent has to stub agent construction. With one call site and a proof of concept's test load, that cost is accepted.
- The prompt lives at `coral/prompts/review.md` and is read at run time with `importlib.resources`. It is Markdown inside the package rather than a string in Python, so changing what Coral looks for means editing prose and the change diffs readably.

## The Review Object

The agent's answer is a structured object, requested through the `response_format` parameter on `create_deep_agent`. It carries a summary and a list of findings. Each finding carries its text and its anchor: a span of lines in a file, a single line in a file, a whole file, or the pull request as a whole. The last two share one posting path and differ only in whether a file is named. The object also carries a flag saying whether an empty finding list means there was nothing to find or means everything Coral would have said is already on the pull request and still stands, because a reader needs those told apart and only the agent knows which it is.

- The review object is the only place structure originates. It is a set of frozen dataclasses handed to the agent framework unchanged, so the type the model fills is the type the posting code reads. There is no wire type and no conversion step.
- A finding's anchor is a union of four frozen dataclasses, each naming itself with a `kind` literal. Reading one is an exhaustive `match` over the four classes, so a fifth kind is a type error at every site rather than a runtime surprise.
- The schema's JSON form uses `anyOf` and no `oneOf`, which is what a strict provider-side validator accepts.
- The agent's structured result is required. Its absence, and a `structured_response` of `None`, are the same failure, and there is no path that recovers a review from prose or substitutes an empty one.

## Triggering

GitHub sends `issue_comment` for a comment on a pull request as a whole and `pull_request_review_comment` for one on the diff, which is why Coral has to answer both — a request means the same thing wherever it is left. Nothing triggers on `pull_request_review`, because GitHub has no endpoint for reacting to a review, so a request arriving that way could never be acknowledged.

A job-level condition throws out deliveries that are certainly not triggers before a runner is allocated. It is a coarse filter and cannot be anything else: Actions expressions offer `contains`, `startsWith`, and `endsWith`, with no regular expressions and no way to work line by line. So on the comment paths the condition tests that the body contains `/coral` at all, that the comment sits on a pull request rather than an issue, and that the author association passes. `issue_comment` fires for comments on plain issues as well as on pull requests, and the two are told apart only by the `pull_request` key on the issue object, so the condition checks for it — an issue number is not a pull request number. Deciding whether the command really stands alone on its own line, unquoted and outside a code fence, needs a real parse of the comment body and happens in the resolve step, which stops the run when the command is inert. The cost is that a comment merely mentioning Coral allocates a runner and then stops within seconds.

On the `pull_request` path the condition also covers the two automatic-review exclusions, read from `draft` and from the author's `type` on the payload. A `type` of `Bot` catches GitHub Apps such as Dependabot, and does not catch a script driving an ordinary user account, which is as far as a payload field can take it. The bot exclusion is deliberately not applied on the comment paths: a bot that has write access and types `/coral` is asking on somebody's behalf, and the reasoning about volume does not apply to a command somebody had to write.

- The workflow triggers on the `opened` and `ready_for_review` types of `pull_request`, and on the `created` type of both `issue_comment` and `pull_request_review_comment`. It does not trigger on `synchronize`.
- Write access is read off the `author_association` field on the comment payload, where `OWNER`, `MEMBER`, and `COLLABORATOR` count as write access. It is already in the payload, so the check costs no API call. It is broader than write access in two directions. `MEMBER` means the author belongs to the organization that owns the repository, which does not by itself grant write access to that repository. `COLLABORATOR` means the author was invited to collaborate, which includes an outside collaborator invited with read-only permission. Both are accepted. Narrowing either means a permissions call on every comment, and the population let through is people somebody deliberately added to the repository or the organization.
- Coral cannot trigger itself, and this costs nothing to arrange. Events created with the job's own `GITHUB_TOKEN` do not create workflow runs at all, excepting only `workflow_dispatch` and `repository_dispatch`. Coral never reading its own comments as a request is therefore a property of the platform rather than a rule Coral has to keep. It stops being free the moment Coral is given an identity of its own, so any future move to a GitHub App has to bring an explicit self-check with it.
- The fork check is a security control on the comment path, not a statement of scope. A comment event fires in the base repository, so a `/coral` on a pull request from a fork would run with the base repository's token and the base repository's secrets, against a branch nobody with write access has vouched for. The resolve step reads the head repository off the pull request and stops when it differs from the base, treating a deleted head repository as a fork. On the `pull_request` path GitHub already withholds secrets and downgrades the token for forks, so the job could not work even if it ran, but Coral filters there too rather than relying on a failure to be the guard.
- Concurrency is a group keyed on the pull request number, with `cancel-in-progress` left false. A run already in progress finishes, and a newly queued run cancels whichever run was pending in that group. That is the whole of "never two reviews at once, and several requests during one review collapse into one further review" — a key in the workflow file rather than a coordination protocol. The number is read from `pull_request.number` or `issue.number` depending on which event fired, and the two cannot collide because GitHub numbers issues and pull requests from one sequence.
- The reaction goes on as soon as the request is accepted and before the review begins, because a comment-triggered run does not appear among the pull request's checks and the reaction is the only sign the person who asked will get until the review lands. Because the concurrency group cancels pending runs, the request that started this run is not necessarily the only one waiting on it. The resolve step is already reading the conversation, so it reacts to every qualifying `/coral` comment that does not already carry Coral's reaction, not only to the one on the triggering payload. That is what keeps the acknowledgment honest for a request whose own run was cancelled before it started.

## The Run

The workflow runs five steps in a fixed order: set up, resolve, check out, review, and report. The middle three carry the work, and the order is what the rest of this document depends on.

The setup step installs `uv` and builds Coral's own virtual environment under the runner's temporary directory, publishing the directory that holds the console script as a step output. It is a step of its own because resolve runs before the checkout and review runs after it, so both need that environment and it can only be built once. The alternative — resolve builds it and the later steps find it at an agreed path — was rejected: it puts environment construction inside the gatekeeper, so the log line saying why a run stopped sits underneath a dependency install, and the coupling between the two actions becomes a convention nothing checks.

The split between resolve and checkout exists because the checkout needs a commit SHA that only an API call can supply. The resolve step asks GitHub for the pull request and reads the head SHA, the base branch's current SHA, the state, the draft flag, and the head repository off the answer. It then fetches the conversation, leaves the reaction, and last of all decides whether there is a review to do at all and stops the run when there is not. The fetch sits ahead of the reaction because the reaction goes to every qualifying request in the conversation rather than only to the one on the triggering payload, and both sit ahead of the gates because the work a gate is worth stopping is the checkout and the agent, not one or two GraphQL calls. The report step runs only on failure.

- A step boundary is a process boundary, and two kinds of thing cross it. Two values cross as step outputs, and both exist because YAML reads them rather than Python: the head SHA, which the checkout step needs, and a `proceed` flag, which the checkout and review steps condition on. Every value written as a step output is a SHA or a boolean, so the heredoc form of the Actions output protocol is not built and an assertion rejects a newline. Everything else crosses as a file under the runner's temporary directory: the pull request as the resolve step fetched it, and the conversation.
- A stopped run is not a failed run. Resolve writes `proceed=false`, says why on stderr, and exits zero, so a pull request Coral declined to review leaves a green run with skipped steps rather than a red one. Only a run that broke ends red.
- Both commits are pinned by the resolve step and neither is read again. The head SHA is the subject of the review, and pinning the base as well is what makes the diff stable: the merge base is computed from two fixed commits, so the change Coral reviews cannot shift underneath it when either branch moves during the run. Neither arrives on an event and neither is a branch name.
- The resolve step stops the run when the command is inert, when the pull request is closed, when the head belongs to a fork, when the change exceeds the size backstop, and, on the two automatic paths only, when this commit has already been reviewed. Each stop comes before the work it would make pointless.
- The change-size backstop is 300 changed files or 30,000 changed lines, checked before the clone. `changed_files`, `additions`, and `deletions` all come back on the pull request fetch, so the check costs no call of its own. Both numbers are chosen rather than measured, and both are backstops set well above anything a person opens by hand, so they are not expected to be tuned.
- The checkout takes the head SHA the resolve step produced, with `fetch-depth: 0` and `persist-credentials: false`. Full history is what makes the merge base exact, which no shallow depth can promise, and it also brings the base SHA into the clone: `fetch-depth: 0` fetches `+refs/heads/*:refs/remotes/origin/*`, so every branch head is present locally. Checking out the resolved SHA rather than the branch matters because the branch may have moved since resolve read it; when it has moved by force-push the SHA can be unreachable and the checkout fails outright, which is one of the cases the report step exists to report. Credential persistence is off because the default writes the token into the repository's own git config as an HTTP header, where the agent would find it by reading a file, and skipping it would hand back everything the secret handling below buys.
- Coral's own virtual environment lives under the runner's temporary directory, outside the workspace, and is never activated and never placed on `PATH`. Every step invokes the console script by absolute path, so the `PATH`, `VIRTUAL_ENV`, and `UV_*` variables in the review step's own process are exactly what the runner set. The checkout between resolve and review therefore cannot disturb it, and keeping Coral's own environment out of the agent's shell is a property of how Coral is invoked rather than a filter with work to do.
- Each run gets a fresh runner with a fresh filesystem. Nothing survives from one review to the next, so there are no leftovers to distrust or clear.

## The Conversation

The conversation does double duty. It is the agent's context, and because every comment Coral posts opens with an invisible marker carrying the reviewed commit SHA, it is also the record of which commits Coral has already reviewed. That is the whole of Coral's memory and the reason there is no database.

- The conversation is fetched with GraphQL rather than REST, because deciding whether a past finding still stands means reading each review thread's `isResolved` and `isOutdated` fields, and REST exposes neither. The query returns the pull request's reviews, its review threads with their comments, and its issue comments, each with its author and author association. Inline comments are read under `reviewThreads` and never under `reviews`: every one of them is reachable both ways, the resolution and staleness flags live only on the thread, and asking both ways returns each comment twice. The job's token reaches `reviewThreads` with the three permissions the workflow declares and nothing more, which is observed from inside a real run rather than read off a document — GitHub publishes fine-grained permission requirements per REST endpoint and publishes nothing equivalent for GraphQL.
- A comment is one piece of prose somebody wrote: an issue comment, a review whose body is not empty, or a comment inside a review thread. A review with an empty body is the envelope GitHub creates to hold a single inline comment, and nearly every review on a busy pull request is one of those, so counting them as discussion would spend the bound on nothing. Such a review is still read for its marker, which keeps the record of reviewed commits independent of how much other people talked.
- The conversation is bounded at the 200 most recent comments and 400,000 characters, whichever binds first, and the review says what was dropped when either does. Both numbers are chosen rather than measured. The size backstop bounds the diff and this bounds the discussion, and without it a long-lived pull request would silently spend the context window on argument rather than on code. The 200 are the most recent across all three connections rather than 200 from each. A review thread is kept when a comment inside it is kept, and a thread that survives keeps its flags, its path, and its lines whole, because those are what decide later whether a finding still stands. The count of what went unread is deliberately generous — it counts an empty-bodied review nobody asked for as a comment — because overstating what Coral did not read is the safe direction for a promise made to a reader.
- A connection may not be asked for more than 100 items, so the bound costs more than one query whenever a pull request is busy enough to reach it. The first query asks all three connections for their newest 100, which covers most pull requests in one round trip. A connection that reports a previous page and has not yet offered enough comments to satisfy the bound is then paged backwards from its own cursor, one small query at a time, capped at four pages so a pull request carrying a thousand empty reviews cannot walk its whole history. The rule is per connection rather than global, and it has to be: the bound takes the most recent comments across all three connections, so a comment can only be missed if its own connection was not paged deep enough to offer it, and a connection that has already offered the whole bound cannot be hiding one that belongs in the answer.
- Ordering is only as good as GitHub's connections allow. Neither `reviews` nor `reviewThreads` accepts an ordering argument, and the only ordering field for issue comments is `UPDATED_AT`, which would rank an old comment edited yesterday above one written last week. So all three take the connection's default order and `last:` is trusted to return the newest, which is observed against a real pull request rather than promised. Every comment carries a timestamp of its own and the bound sorts on that, comparing the strings GitHub returned because they are ISO-8601 in UTC and sort lexically. A review thread carries no timestamp at all, and its recency is the recency of the comments inside it.
- Every comment Coral posts opens with an HTML comment carrying a fixed sentinel and the reviewed commit SHA, invisible in rendered Markdown and exact to match. It goes on the inline findings as well as on the review body, because Coral posts as the repository's automation and that login belongs to every other bot in the repository too, so the author cannot tell Coral's comments from anything else the account writes and the marker has to. The prose naming the commit is for the human reader; the marker is for the next run, and neither substitutes for the other. The set of commits Coral has already reviewed is read back out of review bodies alone, even though every comment carries a marker: an inline finding and a failure comment both name a commit without meaning that commit was reviewed, and a failure comment means the opposite, so reading the set from one connection keeps that distinction free rather than encoding it in the marker.
- The already-reviewed check applies to the two automatic entry points only, where it stops a pull request that is opened ready, converted to draft, and marked ready again from being reviewed twice at the same commit. A review somebody asked for never tests the head, because somebody who asks gets a review whether or not the code has moved.
- The conversation is written to the runner's temporary directory rather than passed between steps as an output. It is too large to be an output, and the temporary directory is outside the workspace, so the checkout does not disturb it. This is what keeps the conversation fetched once rather than twice.
- Every comment handed to the agent is labeled with its author's association, so the difference between an owner and a drive-by account is visible in the input rather than inferred from tone. This does not enforce anything and is not claimed to. It is the cheapest thing that gives the model any basis at all for the judgment it is asked to make about a comment.
- The pull request conversation is untrusted input, and it is untrusted in a way the repository's own contents are not. Anyone who can comment can write into it, including someone with no access to the repository at all, and what they write reaches a model that holds an unsandboxed shell. The write-access check decides who can start a run. It does not decide whose text the agent reads, and the agent has to read all of it. So the reachable attack is this: a stranger leaves a comment, a maintainer later asks for a review, and the stranger's text is in the agent's context while the agent has a shell. Telling the agent that the conversation is information and never instruction is a prompt-level defense, not an enforced one. What actually bounds the damage is the secrets being unreachable from the shell, and the output schema being the agent's only return value, which together keep anything the agent is talked into from becoming a change to the repository or the merge. The residual risk is command execution on a throwaway runner holding a checkout of code that is already public to everyone who can see the pull request. That is accepted for a proof of concept and is the first thing to revisit if Coral is run anywhere that matters.

## The Agent

The agent runs shell commands inside a checkout of the repository under review, and that repository's own code runs in the same place. Its access to the checkout goes through a DeepAgents backend: filesystem operations and shell execution both come from that one object, so the compute target is a single swappable dependency. Coral uses `LocalShellBackend`, rooted at the checkout, behind the middleware described under the time budget. It provides the `execute` tool the agent runs commands and tests with, and its filesystem operations run as direct Python rather than as shelled-out scripts, which matters for an agent that reads and greps heavily against a deadline.

The review step passes the conversation to the agent as part of its input, and constructs the agent only after the working tree exists and after the secrets have been stripped. Setup is not the agent's job.

`create_deep_agent` installs a summarization middleware by default, so a long review has its own context compacted while it runs. Every review is meant to cover the whole change, and that promise is only as good as what survives compaction. This is a reason to keep the conversation bound and the size backstop tight rather than a thing to switch off.

- The agent's only return value is the structured review object, and deterministic code does the posting. There is no output the model can produce that becomes a push, an approval, or a comment Coral did not compose. This constrains what the agent hands back. It does not by itself constrain what the agent's shell does, which is why the missing credentials matter as much as the schema.
- Neither secret is reachable from the agent's shell, and two separate things make that so. The environment the shell gets is built rather than inherited, and neither secret is named in it. And the review step reads the OpenRouter key and the GitHub token out of its own environment at start-up, holds them in memory, deletes them from `os.environ`, and only then constructs the model client and the backend, so any later code that assembles a child environment out of `os.environ` cannot pick them up either. The chat model holds the key it was handed and the posting code holds the token it was handed, so both still work. Without this, an agent with `pull-requests: write` in its environment could submit an approving review with one `curl`, and Coral never approving would be a request rather than a property.
- The job's token is scoped by a `permissions` block naming `pull-requests: write`, `issues: write`, and `contents: read`, and nothing else. It expires when the job ends. There is no key to store, nothing to mint, and nothing to rotate, which is the largest single saving of running inside Actions. The two write permissions are both needed because the reactions divide across two namespaces. A reaction on a comment attached to the diff goes through `/repos/{owner}/{repo}/pulls/comments/{id}/reactions`, which lists Pull requests at write as its only permission set. A reaction on a comment on the pull request as a whole goes through `/repos/{owner}/{repo}/issues/comments/{id}/reactions`, which lists Issues at write as its only permission set. Neither permission grants the other, nothing about the target being a pull request comment moves the issues endpoint into the Pull requests permission, and a request can be left in either place. The failure comment needs neither addition, because the endpoint that posts it accepts Issues or Pull requests at write as alternatives.
- This is not a sandbox, and nothing in the design should be written as though it were. The agent runs arbitrary shell commands as the runner user, with network access, and can read any file on the runner. Keeping the secrets out of its environment is a barrier rather than a boundary: it puts them out of easy reach, and it does not stop a determined agent from going looking elsewhere on the runner. What makes the remaining exposure acceptable is that Coral is the repository's own continuous integration, running the repository's own code on the repository's own runner.
- The agent reaches the checkout only through the backend, and nothing else runs a command inside it on the agent's behalf. Coral's own deterministic code does run `git` against the checkout, in `coral/diff.py`, to compute the diff the anchors are checked against. That is not agent access, and it is what makes the diff the agent saw and the diff the anchors are checked against the same diff. The checkout's location is read from `GITHUB_WORKSPACE` in one place, `coral/runner.py`, and passed from there, so there is one notion of where it lives.
- The environment the agent's shell gets is built explicitly, variable by variable, rather than pared down from Coral's own. `LocalShellBackend` inherits nothing: `inherit_env` defaults to false, and with no environment supplied the shell's environment is empty, which would leave the agent unable to run anything at all. So Coral constructs it. What goes in is what the runner's toolchain needs to work — `PATH`, `HOME`, `LANG`, `TMPDIR`, and the handful of variables a build reads. What stays out is both secrets, `VIRTUAL_ENV`, and every `UV_*`. Building it up rather than filtering it down is what makes the omissions checkable, because a variable is in the agent's shell only if Coral named it. Without this the repository's own `pytest` runs against Coral's interpreter and Coral's packages, and running the repository's tests breaks first and most often on exactly the Python repositories Coral is most likely to be tried on.
- The request names the capabilities it depends on rather than the providers that have them, by setting `require_parameters` on the `openrouter_provider` kwarg of `ChatOpenRouter`. A provider allowlist is not available here: the alias's endpoint list comes back empty, so its provider set cannot be read, which leaves nothing to test and nothing to pin. Capability is also the thing that actually varies — the endpoints serving the concrete release the alias redirects to disagree on structured output and on context window. What makes an unconstrained request dangerous rather than merely variable is that LangChain chooses between native structured output and tool-based structured output from the model profile and not from the serving endpoint, so a profile reporting `structured_output: True` selects the native path for every request, including one routed somewhere that cannot serve it. Requiring the parameters is what keeps the router from sending the request there. The same kwarg carries one more entry, `ignore: ["azure"]`, and Coral has to supply it deliberately: DeepAgents injects that entry itself, but only when it resolves a model handed to it as a string, and Coral constructs `ChatOpenRouter` and passes the instance. The reason the entry exists is a real failure rather than a preference — OpenRouter's `/responses` beta is stateless, so a replayed reasoning item cannot be looked up upstream and the request fails outright.

## Posting The Review

Posting is deterministic code. It checks each finding's anchor against the diff it computed locally, demotes the ones that will not attach into the summary, rechecks that the pull request has not merged in the meantime, and posts one review naming the commit. The summary becomes the review body and the anchored findings become its comments, in one API call. The review is left as a comment, never approving and never requesting changes.

- The anchors are checked against the diff of the two pinned commits, which is the same diff the agent saw. It is computed from the two commits rather than from the working tree, because the agent is allowed to write scratch files into that tree, and it is not refetched from GitHub at posting time, because by then either branch may have moved and the check would be against a change Coral did not review.
- GitHub accepts a review comment only on a line that is part of the diff. Findings whose anchor falls outside it are moved into the summary with their intended file and line named, so no finding is lost. This is expected to fire regularly rather than being an edge case.
- A whole-file finding goes into the summary by construction rather than by failure. The `comments` array on the create-review endpoint accepts only `path`, `position`, `body`, `line`, `side`, `start_line`, and `start_side`, so the `subject_type` that marks a file-level comment has nowhere to go in a batched review. Posting one would mean a second API call per finding, and a run posts one review rather than a comment per finding.
- GitHub accepts or rejects a review as a whole, so one bad anchor costs every finding in it. The local pre-check cannot be sufficient on its own, because GitHub decides what is inside the diff using its own patch generation rather than the workflow's, and because the base branch may have moved since it was pinned. A rejected call is therefore retried, and the retry is unconditional in its effect: every anchored finding is demoted into the summary and the review is posted again with no inline comments at all. Demoting only the anchors GitHub named would be better for the reader and is worth doing when the 422 response identifies them, but it cannot be the mechanism, because a retry that depends on the error naming the offending entry fails silently when it does not. The guarantee worth keeping is that no finding is lost, and a summary-only repost delivers it whatever the error body says.
- The review names the commit it reviewed, in the API call and not only in the prose. Naming it is what puts each comment on the line the agent meant, since GitHub resolves a comment's position relative to a commit. It is also what lets GitHub mark that comment outdated later, when a further push changes the code underneath it, and what makes the record the next run reads back.
- The workflow rechecks the pull request's state immediately before posting. The resolve step's check was minutes ago, and the whole point is not to post advice onto something already merged.

## The Time Budget

A pull request costs one full agent run for its automatic review and one more every time somebody asks, because every review covers the whole change rather than only what is new. Nothing automatic multiplies that, which is why a push does not start a review. A run is paid for whether or not it produced anything: an agent that spends its budget failing to install the repository's dependencies costs the same as one that finds five bugs. On a private repository those minutes are billed, so the cost of Coral is the number of pull requests opened multiplied by the length of a run.

- Coral owns its deadline. The budget is 20 minutes, measured from the start of the review step, with enough headroom left over to post a review afterwards, which means the review step is always still running when its own deadline fires. Everything under "Failure" below depends on this. The number is chosen rather than measured.
- The job's `timeout-minutes` is 30, and it is a backstop and never the mechanism. A job cancelled by GitHub cannot post a failure comment, so Coral's own deadline is set comfortably inside it and is what actually fires. The gap covers resolve, checkout, dependency installation, and posting, and leaves several minutes spare.
- The deadline needs a mechanism, because wanting one does not produce one. It takes all four of: a step cap on the agent loop, set to 200 and applied by overriding the `recursion_limit` on the compiled graph, since DeepAgents sets that to 9,999 and 9,999 is not a limit; an elapsed-time check between steps that ends the run when the budget is spent; a request timeout on the model call, set to 180 seconds so a hung connection cannot outlast the budget, and passed in milliseconds because `ChatOpenRouter` takes `timeout` in milliseconds; and the bounded shell timeout below. All three numbers are chosen rather than measured.
- The per-command shell timeout is capped at 300 seconds by Coral's own `FilesystemMiddleware`, constructed with `max_execute_timeout=300` and handed to `create_deep_agent` through its `middleware` argument. Middleware supplied that way is merged into the assembled stack by name, and `AgentMiddleware.name` defaults to the class name, so Coral's instance replaces the framework's own at its existing position rather than adding a second one. The enforcement is a rejection and not a clamp: a command asking for more than the ceiling does not run, and the model is told the number it may not exceed. Neither of the two obvious alternatives caps anything. `LocalShellBackend(timeout=...)` sets only the default used when the model omits the argument. And a wrapper that holds a backend and forwards to it cannot take over `execute` at all, because the framework decides whether a backend supports execution with an `isinstance` check against `SandboxBackendProtocol`, and decides whether the tool exposes a `timeout` argument by inspecting the class's `execute` signature — a wrapper fails both, and the second failure costs the per-command timeout entirely. Left alone the ceiling is 3,600 seconds, so a model that decides a slow test deserves an hour gets an hour, and the elapsed-time check does not run until the command returns. Replacing the middleware moves three arguments onto Coral that the factory used to pass: the backend, the harness profile's tool-description overrides, and the private permissions list. The backend has to be the same instance every other middleware received, or two notions of where the checkout lives exist. And because the collision is by class-name string, a rename upstream turns the replacement into an addition, leaving two middlewares that each register a `read_file` tool.

## Failure

Every way a review can fail ends in a comment on the pull request. There are two halves and they meet at a marker file. It matters because a person may already have seen Coral react to their request, and a reaction followed by nothing is worse than no reaction at all.

- The review step reports its own failures. Because Coral owns the deadline, a step that runs out of time or throws is still running, still holds the checkout, and is still the deterministic code that posts to GitHub. It posts the failure comment itself, immediately. The comment carries the reason and nothing else, and the partly built review object is dropped. Before returning, the step writes a marker into the runner's temporary directory recording that the failure has been reported.
- A final report step, conditioned on the job having failed, posts the failure comment for everything the review step could not. Resolve can fail on a rate-limited API call or a missing secret, the checkout can fail on a force-pushed SHA or a full disk, and dependency installation can fail on its own. None of those reach the review step, and all of them leave a person who has already seen Coral's reaction waiting for a review that will never arrive. The step skips when the review step's marker is present, so a failure is reported once.

A run that dies in a way no step can report — the runner itself vanishing, or the job being cancelled by GitHub's own timeout — is visible as a failed run in the repository's Actions tab, with its logs. Nothing else has to watch for it, and the recovery is that a person asks again.

## The Runner

A standard GitHub-hosted Ubuntu runner gives 4 vCPU and 16 GB of RAM on a public repository, and 2 vCPU and 8 GB of RAM on a private one. Both give 14 GB of SSD. Larger runners are available to organizations on Team and Enterprise Cloud plans. Submodules are not initialized and Git LFS pointers are not resolved; both are a single input on the checkout, so this is a default rather than a limit.

- Coral runs directly on the runner and never inside a container of its own. This is what makes running the repository's own tests possible at all. A container action would hand the agent Coral's image, which knows nothing about the repository under review, and running that repository's tests needs that repository's toolchain. GitHub's hosted runner images carry a broad preinstalled toolchain, and inheriting it is the only reason Coral can run a test in a repository it has never seen. The cost is that Coral's own dependencies are installed beside the repository's, which the built-up shell environment keeps out of the way.
- The workflow file on the comment paths is always read from the default branch, so a pull request cannot change how it is reviewed by asking. On the `pull_request` path the file comes from the pull request's own head, so a pull request can change the workflow that reviews it — disable Coral, alter its prompt, widen the `permissions` block, or read the OpenRouter key. That population is people with write access, running code on a runner that already holds the repository's secrets, so it is the same trust every other job in the repository is given. It is recorded because it is not obvious.

## Numbers Chosen Rather Than Measured

The conversation bound, the change-size backstop, the deadline, the job timeout, the step cap, the model request timeout, and the per-command shell ceiling are all chosen rather than measured. They are stated so the design is complete and testable, not because any of them is known to be right. The first real reviews against real repositories are what settle them.

## Undecided

Decisions arrive here before they are made, not after.

- **Whether GitHub's 422 identifies the offending anchor.** The blunt retry does not depend on it and is correct either way. If the error body does name the bad entries, the retry can demote only those and keep the rest inline, which is strictly better for the reader.
- **Which provider actually serves the alias**, and whether a native structured-output request succeeds against it. Requiring the parameters in the request is written to survive either answer.
