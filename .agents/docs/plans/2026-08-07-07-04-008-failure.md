# Failure

Roadmap: item `8`, `Failure`.

## What Was Checked

- `coral report` exists in `coral/cli.py` as a subcommand whose handler is a `report()` that raises `NotImplementedError`. There is no `actions/report/` and the reusable workflow has no fifth step, so nothing invokes it today.
- `DeadlineMiddleware.before_model` in `coral/agent.py` raises a `RuntimeError` whose message already reads as a sentence a person can act on, and ends with "No review was posted." That sentence moves into the comment's own prose, so the exception stops carrying it.
- Every failure path out of `coral review` is an exception propagating out of `review()`. Nothing catches, so nothing is lost by wrapping the body in one `try`.
- `post_comment` in `coral/github/post.py` already posts a plain marker-carrying comment on the pull request as a whole. The size stop uses it; the failure comment is its second caller and needs no new posting code.
- `signed()` and `marker()` require a commit. A comment-triggered run whose `resolve` fails before the fetch returns has no commit to name: the pull request was never fetched, and an `issue_comment` payload carries no head SHA. The marker has to tolerate that.
- `is_request` in `coral/command.py` and `is_mine` in `coral/github/conversation.py` both ask "did Coral write this?" by way of `reviewed_commit(body) is not None`. A marker naming no commit breaks both, which is what moves the question into `coral/github/marker.py` as its own function.
- `reviewed_commits` reads review bodies only, so a failure comment carrying a marker never enters the record of reviewed commits however it is spelled.
- The job condition is coarse, so a comment merely mentioning `/coral` mid-sentence allocates a runner. A run that fails there owes nobody a comment, and the report step is the only place that can tell.
- Word counts: `roadmap.md` 3,498 of 3,500 and `testing.md` 1,498 of 1,500, both of which grow here and must be paid for by trimming built items' prose. `architecture.md` is 1,410 of 1,500. `functional-requirements.md` is 1,496 of 1,500 and needs no change: everything item 8 builds is already written under "Failure".

## Goal

A run that produces no review says so on the pull request, exactly once, in enough detail to tell retrying from investigating. The review step reports its own failures, because it is the step holding the reason. Everything before it is reported by a step that runs on job failure and stays quiet when the review step already spoke.

## Approach

### The marker stops requiring a commit

`coral/github/marker.py`:

```python
def marker(commit: str | None) -> str:
    """The line every comment Coral posts opens with, naming the commit when there is one."""

def is_mine(body: str) -> bool:
    """Whether Coral wrote this, which the sentinel answers whether or not a commit follows it."""
```

`marker(None)` produces `<!-- coral:reviewed -->`; the pattern makes ` commit=<sha>` an optional group, and `reviewed_commit` keeps returning the SHA or `None`. `is_mine` moves here from `coral/github/conversation.py`, which imports it, and `is_request` in `coral/command.py` switches to it as well. Without that switch a failure comment naming no commit is a comment Coral does not recognize as its own.

`signed(commit: str | None, body: str)` in `coral/github/post.py` and the `commit` parameter of `post_comment` widen the same way. `review_payload` is untouched: a review always names a commit.

### The report step knows two things and neither of them is the exception

`coral/report.py`:

```python
REASON_LIMIT: Final = 1_000

def described(error: BaseException) -> str:
    """The exception as the pull request sees it: its type, its message, and no more than fits."""

def failure_comment(reason: str | None, run_url: str) -> str:
    """What Coral says when a run produced no review."""

def owed(event: Event) -> bool:
    """Whether this run owes the pull request a comment about failing."""

def report() -> None:
    """The report step: say that the run failed, unless the review step already did."""
```

`described` is `f"{type(error).__name__}: {error}"`, cut to `REASON_LIMIT` characters with an ellipsis. `failure_comment` puts it in a four-backtick fence, so a message holding backticks or newlines cannot reshape the comment, and follows it with a link to the run and a line saying `/coral` starts a fresh review. A `None` reason drops the fence and the comment says the run failed and points at the log.

The report step passes `None`: it never saw the exception, and the step that did is the step that posts it. Which step failed is not named either — the run link is one click from that, and passing the step outcomes in as action inputs is plumbing bought for nothing.

`owed` is the whole of the report step's judgment, and it is two questions:

- Has the review step already reported? `runner.reported_path().exists()`.
- Did this delivery ask for anything? A comment event whose body is not a request under `is_request` asked for nothing, so a run that fails on a mid-sentence mention of `/coral` stays silent. A `pull_request` delivery always asks, the workflow's condition having already excluded drafts and bots.

Neither question costs an API call, which matters: the failure being reported is often the API refusing to answer.

The commit the comment names comes from `runner.pull_request_path()` when resolve got far enough to write it, and is `None` otherwise. Reading that file is not the same as knowing the run proceeded — resolve writes it before the gates — but a commit on the comment is a label, not a decision.

### The review step reports itself

`coral/review.py` reads the credentials and the pull request as it does now, then wraps everything from the conversation onwards in one `try`:

```python
    try:
        ...
        post_review(github, owner, repo, number, head, review, added)
    except Exception as error:
        log.exception("The review failed; reporting it on the pull request.")
        post_comment(
            github, owner, repo, number, head, failure_comment(described(error), runner.run_url())
        )
        runner.reported_path().write_text("")
        raise
```

Three things about that block:

- The file is written after the post, not before. A post that fails writes nothing, so the report step still owes the comment, and the guarantee reads the same in both directions: the file exists only when a comment landed.
- The exception is re-raised. A run that could not review is red, which is what "only a broken run is red" in `.agents/docs/architecture.md` says.
- Everything above the `try` — reading `GITHUB_TOKEN`, `OPENROUTER_API_KEY`, and the pull request off disk — is outside it, because a failure there leaves Coral without the client or the identity it would post with. That is the report step's to cover, and it does.

The deadline is inside the block like everything else. Its message is already the sentence Coral wants to post, so `DeadlineMiddleware` drops the trailing "No review was posted." that `failure_comment` now says once.

### The workflow gains a fifth step

`actions/report/action.yml` takes `coral-bin` and `github-token` and runs `"$CORAL_BIN/coral" report`, the same shape as `actions/resolve/`.

```yaml
      - if: failure() && steps.setup.outcome == 'success'
        uses: $/actions/report
        with:
          coral-bin: ${{ steps.setup.outputs.bin }}
          github-token: ${{ github.token }}
```

`failure()` covers a failure in any earlier step, including one in a step that was skipped past. The guard on setup is the honest half: a setup failure leaves no console script to run, so it joins the runner vanishing and GitHub's own timeout as a death that is visible in the Actions tab and nowhere else. Skipping the step says that in the run's own log rather than as a missing-file error.

`coral report` exits zero whether or not it posts. The job is already failed; a report step that fails on top of that adds nothing.

### `coral/runner.py` gains two paths

```python
def reported_path() -> Path:
    """The file the review step writes once it has reported its own failure."""

def run_url() -> str:
    """This job's run in the Actions tab, which is where a failure comment sends the reader."""
```

The first is `RUNNER_TEMP/coral/reported`, beside the pull request and the conversation, and is how the two halves of this item avoid speaking twice. The second is `GITHUB_SERVER_URL`, `GITHUB_REPOSITORY`, and `GITHUB_RUN_ID` joined into a URL.

## Test plan

**Key behaviors to verify**

- `marker`: with a commit, unchanged; with `None`, the sentinel alone. `reviewed_commit` reads the SHA back out of the first and answers `None` for the second. `is_mine` is true for both and false for prose that merely mentions Coral.
- `is_request` is false for a comment carrying a commit-less marker and a line that is exactly `/coral` — the self-exclusion that the optional commit could have broken.
- `described`: the type and the message; a message past `REASON_LIMIT` is cut and ends in an ellipsis; a multi-line message survives whole up to the limit.
- `failure_comment`: with a reason, the fence holds it and the run URL is in the body; with `None`, there is no fence; both carry the link.
- `owed`: false when the reported file exists; false for a comment event whose body only mentions `/coral`; true for a comment event that is a request; true for a `pull_request` event. Written the way `tests/test_runner.py` writes its cases — a payload on disk and `RUNNER_TEMP` pointed at `tmp_path`, which is the runner's own protocol rather than a fake.
- `post_comment`'s body for a commit-less comment opens with the bare sentinel.

**What NOT to test**

- `report()` end to end, which needs a `GitHub` that posts. Its judgment is `owed` and its prose is `failure_comment`, and both are tested directly.
- The review step's `except` block, which needs a review that fails on the way to GitHub. Live checks 1 and 3 are what cover it.
- `run_url`, which is three environment reads joined by slashes.
- Whether Actions runs a step on job failure, or skips it when setup failed. Live check 2.

**Live checks**

1. Set `STEP_BUDGET_SECONDS` in `coral/deadline.py` to about 60, push, and ask for a review of a change big enough to outlast it. Expect exactly one comment naming the elapsed seconds and the budget, a red run, and a report step logging that the review step already reported. Restore the constant.
2. Put a `raise RuntimeError("live check")` at the top of `resolve()`, push, and comment `/coral`. Expect one comment saying the run failed with no reason and a link to it, and a red run. In the same state, comment a mid-sentence mention of `/coral`: a red run and no comment. Revert.
3. Set the test repository's `OPENROUTER_API_KEY` secret to a broken value and ask for a review. Expect one comment carrying the provider's own error inside the fence — the review step's failure path on something that is not the deadline. Restore the secret.
4. A run that succeeds posts its review and nothing else, the report step skipped. The control for all three above.

## Not doing

- **Naming the failed step in the comment.** It would mean passing `steps.*.outcome` into the report action and picking the first failure out of them in a YAML expression. The run link is one click from the same answer.
- **Reporting a setup failure.** There is no Coral to run. Deliberate, and the roadmap says so rather than promising a comment that cannot come.
- **Retrying anything.** A failed run is asked again with `/coral`, which the comment says.
- **Checking that the pull request is still open before the failure comment.** A comment on a pull request that closed mid-run is harmless, and the check costs a call on a path where calls are what failed.
- **Reporting a job GitHub cancels** — its own `timeout-minutes`, a lost runner. No step runs, so no step posts.
- **Suppressing the comment when a run fails on a pull request Coral would have declined** — a fork, a closed pull request — because resolve died before the gates ran. Rare, and one comment saying a run failed is not worth a second fetch to avoid.
- **Adding `REASON_LIMIT` to item 9's list of numbers.** It bounds a comment body against an unbounded exception message; no run measures it.
