# Posting

Roadmap: item `7`, `Posting`.

## What Was Checked

- `everything_already_said` has carried the contract since item 1 and nothing reads it. The posted body is the marker, the commit line, and the model's summary; the distinction between "nothing to find" and "everything already said still stands" that `.agents/docs/functional-requirements.md` promises under "Output" is not on the pull request today. Posting is where that field gets its reader, so item 7 closes it.
- `added_lines(workspace, first, second)` diffs two commits, so neither `reset()` nor the agent's scratch files can move it. Computing it beside `diff_text` in `coral/review.py` makes it the same merge base and therefore literally the same diff the agent read.
- `AddedLine` is a frozen dataclass, so it hashes, and membership is a plain `set` lookup with no new type.
- `coral/github/client.py` raises one `RuntimeError` for every failed call. A 422 cannot be told from a 500 without matching on the message text, so the retry needs a typed failure carrying the status.
- Word counts: `roadmap.md` 3,489 of 3,500, `testing.md` 1,447 of 1,500, `architecture.md` 1,411 of 1,500. Each grows here and the documentation step trims to pay for it. `functional-requirements.md` is 1,496 of 1,500 and needs no change — everything item 7 builds is already written there.

## Goal

The findings that survived verification reach the pull request, all of them, on one call. Anchors are checked against the pinned diff before the call; whatever will not attach is demoted into the summary naming its place; a review GitHub rejects whole is reposted with every finding demoted. The pull request's state is rechecked immediately before posting, and a review with no findings says which of the two empty outcomes it is.

## Approach

### The anchor check lives with the diff

`coral/schema.py` gains `where(anchor) -> str`, moved from `coral/review.py` unchanged: an anchor's prose form, read now by the verifier's request and by a demoted finding's label in the summary. It goes to `coral/schema.py` because that is the one module both readers already depend on, and it stays a pure function over the anchor types with no new import.

`coral/diff.py` gains the check:

```python
def attachable(anchor: Anchor, added: set[AddedLine]) -> LineAnchor | SpanAnchor | None:
    """The anchor GitHub will take a comment on, or None when the finding must be demoted."""
```

- A `LineAnchor` attaches when its path and line are in `added`.
- A `SpanAnchor` attaches when both endpoints are. The lines between are not checked: a span covering a function crosses unchanged lines, and demoting every one of those would leave almost no span anchored. A span whose endpoints sit in different hunks is the case this lets through, and the retry below is what covers it.
- A `SpanAnchor` whose endpoints are equal comes back as a `LineAnchor`. GitHub takes `start_line` as strictly before `line`, and a one-line span is a single-line comment rather than a finding to lose.
- A `SpanAnchor` running backwards, `start_line` above `end_line`, comes back `None`.
- `FileAnchor` and `PullRequestAnchor` come back `None` always. This is where "whole-file findings go to the summary by construction" is one line rather than a rule stated twice.

The set holds added lines only, so a finding on an unchanged line inside a hunk demotes even though GitHub would have accepted a comment there. That is the conservative direction — a demoted finding is still delivered, a rejected review costs a second call — and it is why the roadmap expects demotion to fire regularly. `parse_added_lines` is untouched.

### A rejected call is told apart by its status

`coral/github/client.py` replaces the bare `RuntimeError` with:

```python
class ApiError(RuntimeError):
    """A GitHub call that did not succeed, holding what the caller may act on."""

    def __init__(self, method: str, path: str, status: int, body: str) -> None:
        super().__init__(f"{method} {path} returned {status}: {body}")
        self.status = status
        self.body = body
```

The one place in Coral that recovers differently from a failed call is the retry below, which is the condition `.agents/docs/code-style.md` sets for defining an exception at all. It subclasses `RuntimeError`, so nothing that catches or asserts on `RuntimeError` today changes. Item 8 reads `.body` for the failure comment.

### The payload is built once and posted twice

`coral/github/post.py` splits composition from the call:

```python
def review_payload(commit: str, review: Review, added: set[AddedLine]) -> dict[str, Any]:
    """The create-review body: what attaches as a comment, and what the summary carries instead."""
```

Each finding runs through `attachable`. A `LineAnchor` becomes `path`/`line`/`side`, a `SpanAnchor` becomes `path`/`start_line`/`line`/`side`, and a `None` becomes a demotion. `rendered_finding` produces the prose in both cases, so a finding reads the same wherever it lands.

```python
def demotion(finding: Finding) -> str:
    """A finding that will not attach, naming the place it concerns."""
```

A `PullRequestAnchor` finding gets no label — it concerns no place. Everything else is prefixed `**{where(finding.anchor)}** — `, so a demoted line finding names its file and its line, which is what the requirement asks for.

The demoted entries follow the summary under one lead-in line, `Findings not anchored to a line:`, neutral because both causes land in the same list: a whole-file finding was never going to attach, and a line finding that could not is not the reader's problem.

Then the retry:

```python
def post_review(github, owner, repo, number, commit, review, added) -> Any:
    path = f"/repos/{owner}/{repo}/pulls/{number}/reviews"
    try:
        return github.post(path, review_payload(commit, review, added))
    except ApiError as rejection:
        if rejection.status != 422:
            raise
        log.warning("GitHub rejected the anchored review: %s", rejection.body)
        # Nothing attaches to an empty set, so every finding lands in the summary. The retry is
        # the same composition rather than a second path through it.
        return github.post(path, review_payload(commit, review, set()))
```

The retry is unconditional in what it demotes: it does not read the 422 body for which entry was bad, because a retry that depends on the body naming one fails silently on a body that does not. The body is logged rather than parsed, and reading it on a live run is what settles the question under "Undecided" in `.agents/docs/architecture.md`. Only 422 retries; any other status is a failure item 8 reports.

### A review with no findings says which kind of nothing it is

```python
def nothing_to_report(review: Review) -> str:
    """Which of the two empty outcomes this is, in Coral's words rather than the model's."""
```

Appended to the body when the posted review has no findings: everything already said still stands, or there was nothing to find. Coral writes the sentence rather than trusting the summary to make the distinction, because a second "nothing found" that reads as retracting the first review is the failure this field exists to prevent.

A review whose findings were all rejected by the verifier arrives here empty with the flag the reviewer wrote while it still had findings, which is false, so it reads as nothing to find. Correct enough: nothing survived, and a rejected finding is posted nowhere.

### The state is rechecked at the last moment

```python
def is_open(github: GitHub, owner: str, repo: str, number: int) -> bool:
```

One fetch of the pull request, reading `state`. `coral/review.py` calls it immediately before posting and returns without posting when it is false: resolve's check was minutes and two agent runs ago, and a review landing after the merge is advice nobody can act on. A merge in the last seconds still wins the race, which `.agents/docs/functional-requirements.md` already accepts.

### `review()` ends with the pinned diff in hand

```python
common = merge_base(workspace, base, head)
diff = diff_text(workspace, common, head)
added = set(added_lines(workspace, common, head))
...
if not is_open(github, owner, repo, number):
    log.info("Pull request %d is no longer open; posting nothing.", number)
    return
post_review(github, owner, repo, number, head, review, added)
```

The merge base is hoisted out of the `diff_text` call so both halves take the same one. `added` is computed before either agent runs, next to the diff it comes from, which is where the architecture's rule that the agent's diff and the anchors' diff are one diff is visible in the code.

## Test plan

**Key behaviors to verify**

- `attachable`: a line anchor on an added line comes back; one on a line not in the set comes back `None`; the right path with the wrong line and the right line with the wrong path both come back `None`; a span with both endpoints added comes back a span; a span missing either endpoint comes back `None`; a span whose endpoints are equal comes back a `LineAnchor` on that line; a backwards span comes back `None`; a file anchor and a pull-request anchor come back `None` against a set that contains their lines.
- `review_payload`: a line anchor produces one comment with `path`, `line`, `side: RIGHT`, and a marker-signed body; a span produces `start_line` and `line`; the top-level body carries the marker, the commit, and the summary; `commit_id` is the reviewed commit and `event` is `COMMENT`.
- Demotion: an unattachable line anchor lands in the body naming its file and its line; a file anchor lands naming its file; a pull-request anchor lands with no place prefix; each is a list item that keeps its `<details>` block inside itself.
- No finding is lost: over a review whose findings mix all four anchor kinds against a set that attaches some of them, every finding's body appears exactly once across the comment bodies and the review body. The same assertion with an empty set — which is the payload the retry posts — puts every finding in the body and leaves `comments` empty. This is the done condition asserted directly.
- `nothing_to_report`: the two flag values produce different sentences, and neither appears on a review that has findings.
- `where()` still produces what the verification request expects, from its new home.

**What NOT to test**

- The retry's control flow. Recovering from a 422 needs a `GitHub` that fails, which is a fake of Coral's own code; `.agents/docs/testing.md` rules that out. What makes the retry correct is that its payload is `review_payload` with an empty set, and that payload is unit-tested. Whether GitHub answers 422 at all is live check 2.
- `is_open`, which is one fetch and one key.
- Whether GitHub accepts a comment on a given line. That is the whole reason the retry exists.

**Live checks**

1. Open a pull request whose change gives Coral something to find. Expect: inline comments landing on the lines the findings name, and any finding Coral could not attach in the summary with its file and line. Read it on the pull request rather than in the run log.
2. Force the rejection: temporarily edit `attachable` to return every line anchor shifted well past the end of its file, push, and review a pull request that produces at least one line finding. Expect one review whose summary carries every finding and no inline comments, and a warning in the step log holding GitHub's 422 body. Read that body for whether it names the offending entry — that is the observation the "Undecided" bullet is waiting on. Revert the edit afterwards.
3. Comment `/coral`, wait for the review step to start, and close the pull request before it finishes. Expect a green run, nothing posted, and a log line saying the pull request is no longer open.
4. Open a pull request with a trivially clean change and read the posted review for the sentence saying there was nothing to find. Ask again with no new commits and read the second review for the other sentence — the distinction that keeps a second empty review from reading as a retraction.

## Not doing

- **Reading the 422 body to demote only the entry it names.** The blunt retry delivers every finding either way. Live check 2 records what the body says; if it names entries, that is a later refinement, not this item.
- **Posting a whole-file finding as its own comment.** One call per finding, and the batched `comments` array has no `subject_type` field to put it in.
- **Widening the attachable set to context lines.** It would need hunk bodies rather than hunk headers, which is a real change to `parse_added_lines`. Worth doing only if live runs show demotion firing on findings GitHub would have taken.
- **GitHub's 65,536-character limit on a comment body.** A review whose findings all demote carries every regression test in the summary and could cross it, and the second 422 propagates as a failure. Named rather than handled: whether it happens is a question for real runs, and item 8 makes it a comment rather than a red run.
- **Explaining the demotion to the reader.** The lead-in line says the findings are not anchored, not why. A rejected anchor is Coral's problem.
- **The failure comment.** Item 8. Everything item 7 raises — a non-422 status, a second rejection, a closed pull request — is a red run until then, except the closed one, which is green and silent.
