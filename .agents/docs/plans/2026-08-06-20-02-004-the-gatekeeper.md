# The Gatekeeper

Roadmap: item `4`, `The gatekeeper`.

## What Was Checked

Four things were checked against the live API while this plan was written, because the plan leans on them and no document in this repository states them.

- `IssueComment`, `PullRequestReviewComment`, and `PullRequestReview` all carry `databaseId`, and it is the number the REST reaction endpoints take. The conversation currently keeps only the GraphQL node id, which those endpoints do not accept.
- All three also carry `reactionGroups { content viewerHasReacted }`. Asked against `cli/cli` 10513 it returns all eight reaction contents on every comment, each with a boolean saying whether the token's own account has left that reaction. There is no `viewerHasReacted` field directly on a comment; the only route to the answer is through the groups.
- `GET /repos/{owner}/{repo}/pulls/{number}` returns `changed_files`, `additions`, `deletions`, `head.repo.id`, and `base.repo.id` on the single-pull-request response, so the size gate and the fork gate both read the fetch the resolve step already makes.
- `contains()` in an Actions expression is not case sensitive, and neither is `==`. The workflow's job-level condition therefore lets `/CORAL` through to a runner, which is why the case the command parser accepts is a decision this item has to make rather than one the condition already made.

Two things GitHub documents, restated because the code depends on them.

- Posting a reaction that is already there returns 200 and creates nothing. A reaction Coral leaves twice is a wasted call and never a duplicate.
- A fenced code block in GitHub-Flavored Markdown opens on a line of three or more backticks or tildes indented no more than three spaces, and closes on a line of the same character, at least as long, with nothing after it. A fence left unclosed runs to the end of the comment.

## Goal

`coral resolve` becomes the gatekeeper the rest of the design assumes it is. It pins both commits, acknowledges every request it can see that is owed an acknowledgment, and stops the run at each of the five gates for the reason that gate exists.

The deliverable is `coral/command.py`, the gates in `coral/resolve.py`, a reaction pass over the whole conversation rather than over the triggering payload alone, and the test suite starting in earnest against the parser.

This is the last item before the agent. Everything after it assumes a run that reaches the review step is a run that should be reviewed, and this is what makes that true.

## Approach

### What counts as a request, in one function

`coral/command.py` answers two questions that always travel together: does this comment carry the command, and may this person ask. Both are read off a comment body and an author association, and nothing else, so the same function answers for the comment on the triggering payload and for every comment in the fetched conversation.

The parse walks the body line by line, tracking whether it is inside a fenced code block, and a line counts when it is exactly `/coral` with nothing before it and nothing after it but whitespace.

That single rule is what makes the listed inert forms inert, and most of them need no branch of their own.

- Mentioned in a sentence — the line is not the command and nothing matches.
- Wrapped in backticks — the line is `` `/coral` ``, which is not the command.
- Quoted with a blockquote marker, which is what GitHub's quote-reply button produces — the line begins with `>`, so it is not the command. This is the case the roadmap names, and it falls out rather than being handled.
- Indented, whether by the four spaces of a Markdown code block or by one stray space — leading whitespace is something before the command on that line.
- Inside a code fence — this is the one form the equality rule cannot see, because the line inside the fence really is exactly `/coral`. It is why the walk tracks fence state at all.

Trailing whitespace is allowed, because it is invisible in a rendered comment and a person who left it cannot tell that they did. Two trailing spaces are a Markdown hard line break and are just as invisible.

The command is spelled in lower case and matched exactly. It is a command rather than a word, one spelling is one thing to test and one thing to document, and `README.md` writes it lower case. The cost is that `/Coral` reaches a runner, because the workflow's condition is case-insensitive, and then stops with the run reporting an inert command. That is the same outcome as any other near miss, and the alternative — folding case in Python while the requirement, the README, and every example say `/coral` — buys a spelling nobody was told about.

Write access is the association set the workflow's condition already names: `OWNER`, `MEMBER`, and `COLLABORATOR`. Repeating it in Python is not a duplicate check of the same thing, because the condition tested one comment and this tests every comment in the conversation. Applying it to the triggering comment as well costs one set membership and means there is one definition in the codebase of who may ask, rather than a Python function that trusts a YAML expression it cannot see.

A comment carrying Coral's marker is never a request. Coral cannot trigger itself today, because an event created with the job's own token starts no run, and the filter is here because that property expires the moment Coral is given an identity of its own.

### The reaction goes to every request that is owed one

The resolve step already fetches the conversation before it reacts, which item 3 arranged for exactly this. What changes is which comments get a reaction.

A comment is owed one when it is a request, when Coral has not already left one on it, and when it is a comment rather than a review. Reviews are excluded because GitHub has no endpoint for reacting to one, which is also why the body of a submitted review is not a place to ask.

Whether Coral already reacted comes back on the conversation query, as `reactionGroups { content viewerHasReacted }` on each comment. The alternative is a REST call per comment before the reaction, which doubles the calls to save a field. The viewer that field is answered for is the account the job's token belongs to, and whether that resolves the way Coral needs is the one thing here that a run has to settle. It fails safe: if the field always reports false, Coral reacts to a comment that already carries its reaction, GitHub answers 200, and nothing is created.

The reaction endpoints take a REST comment id, and the conversation currently holds only the GraphQL node id, so `databaseId` joins the query too. The namespace follows from where the comment lives: a comment on the pull request as a whole reacts through the issues endpoint, a comment inside a review thread through the pulls endpoint. That is the split the two write permissions exist for, and reading it off the conversation rather than off the payload is what extends it past the triggering comment.

The comment on the triggering payload is reacted to as well, and it is not read out of the conversation. It is nearly always in there, and nearly always is not always: the conversation is bounded, a thread is read twenty comments deep, and the paging stops at four pages, so a request on a busy pull request can be a request the fetch did not offer. Reacting to it from the payload and dropping it from the list when the conversation already produced it costs one comparison and closes that hole. The payload is also the only place its body and association can be read without another call, so `coral/runner.py` carries both onto the `Comment` it already builds.

A request older than the bound gets no reaction from this pass. It got one from its own run, and the case this pass exists for — a run cancelled while it was pending, whose request nobody acknowledged — concerns the most recent comments by construction.

### The five gates, and where each one sits

The gates come after the reaction, which is what item 3 built and what the architecture asks for: somebody whose request Coral is about to decline still deserves to be told it was heard, and a comment-triggered run gives them no other sign. The work a gate is worth stopping is the checkout and the agent, not the two GraphQL calls that came before it.

They run in this order, and each stop writes `proceed=false`, says why on stderr, and exits zero.

1. **The command is inert.** Comment paths only. There was no request, so there was nothing to acknowledge either, and the reaction pass has already skipped it for the same reason.
2. **The pull request is closed.** Already built. A review that lands after the merge is advice nobody can act on.
3. **The head lives in a fork.** The head repository's id differs from the base repository's, or the head repository is gone, which is what a deleted fork looks like and is treated as a fork. Ids rather than names, because a repository can be renamed and an id cannot be reused.
4. **This commit has already been reviewed.** The two automatic paths only. The head SHA is in the set the markers produced, which is a pull request opened ready, converted to draft, and marked ready again. Somebody who asks gets a review whether or not the code has moved, so this gate never sees a comment path.
5. **The change is larger than Coral will read.** More than 300 changed files or more than 30,000 changed lines, both read off the pull request fetch and both chosen rather than measured.

The order is what decides which reason a person is given when more than one applies, and the last two are ordered deliberately. A closed pull request and a fork are reasons Coral was never going to look at this change at all, and neither of them should be reported as the change being too large.

### The size gate is the one stop that says so out loud

"What Coral Does" in `.agents/docs/functional-requirements.md` says a change too large to review is not reviewed, that Coral says the change exceeds what it will read, and that it posts nothing else. Saying so means a comment on the pull request. Every other gate is silent, and each of them can be: an inert command asked for nothing, a closed pull request and a fork are states a person can see for themselves, and a commit already reviewed has Coral's earlier review sitting on it.

The size gate is the only one where somebody is left waiting for a review that is not coming with nothing on the pull request to explain it. This is also the only gate that can stop an automatic review, on a pull request whose author never asked for anything and has no reason to look at the Actions tab.

It is not the failure comment item 8 builds. A change too large to review is not a failure, the run is green, and the comment says what Coral will not do rather than what went wrong. What the two share is the transport, so `coral/github/post.py` gains a function that posts one issue comment, item 8 uses it for the failure comment, and the comment carries the marker so that a later run recognizes it as Coral's. It does not pollute the record of reviewed commits, because that record is read from review bodies alone.

### The gates are a function, not a step

Every gate reads a field off the pull request, the event, or the conversation, and none of them makes a call. That makes them testable without a network, and they are written that way: one function taking the event, the pull request reduced to the six fields the gates read, and the conversation, returning either nothing or the reason the run stops and the comment that reason owes the pull request.

Reducing the pull request first is what keeps that function honest. The step writes the pull request to disk verbatim, because the review step reads it back rather than fetching it twice, and reaching into the raw JSON from the gate function would make its tests build nested payloads to assert one boolean.

## Related code

- `coral/resolve.py` — fetches the pull request, writes it, fetches and writes the conversation, reacts to the triggering comment, and gates on the pull request being open. Every part of this item lands here or is called from here.
- `coral/github/reactions.py` — the two namespaces, currently reacting to the comment on the payload and nothing else.
- `coral/github/conversation.py` — the fragments each gain `databaseId` and `reactionGroups`, and the comment dataclasses gain the two fields those produce. `reviewed_commits` on the bounded conversation is what the already-reviewed gate reads.
- `coral/github/marker.py` — `reviewed_commit` is how a comment is recognized as Coral's, which the request predicate needs.
- `coral/github/post.py` — gains the plain issue comment the size gate posts, beside the review it already posts.
- `coral/runner.py` — `Comment` gains the body and the association off the payload.
- `.github/workflows/coral.yml` — the job-level condition, which is the coarse half of this item's filtering and does not change.
- `.agents/docs/code-style.md` — name the shape rather than nesting containers, no quiet fallbacks, `Final` constants for tuning values, and a small frozen dataclass for a reportable problem rather than an exception taxonomy.

## Current state

- `coral/command.py` does not exist. Nothing in Coral parses a comment body.
- `coral/resolve.py` applies one gate, on the pull request being open, and reacts only to the comment that triggered the run.
- `coral/github/conversation.py` returns comments carrying a node id, an author, an association, a body, a timestamp, and whether Coral wrote them. Nothing carries a REST id or any reaction state.
- `coral/runner.py` reduces the payload comment to an id and a namespace.
- `coral/github/post.py` posts a review and nothing else.
- The tests are `tests/test_client.py`, `tests/test_conversation.py`, `tests/test_diff.py`, `tests/test_marker.py`, `tests/test_runner.py`, and `tests/test_schema.py`. There is no fixture directory and no mocking library.
- `kkestell/coral-test` has Coral installed on its default branch, pinned at `@main`, and the live checks for items 2 and 3 passed there.

## Test plan

The parser and the gates are decided without a network and are unit tests. Everything that crosses into GitHub is a live run.

**Key behaviors to verify**

- A comment whose only line is `/coral` is a request, and so is one where that line sits among paragraphs of prose above and below it.
- Trailing whitespace after the command does not make it inert.
- A comment with several `/coral` lines is one request.
- A comment from `OWNER`, `MEMBER`, or `COLLABORATOR` is a request; one from `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR`, and `NONE` is not.
- A comment carrying Coral's marker is not a request whatever else is in it.
- The reaction pass returns the issue comments and thread comments that are requests, each with the namespace its endpoint lives in, and skips the ones already carrying Coral's reaction.
- The reaction pass skips a review whose body is a request, because there is no endpoint for it.
- The triggering comment is reacted to once when the conversation also offered it, and once when the conversation did not.
- Each gate stops the run, and the reason names the gate.
- The already-reviewed gate stops an automatic run whose head SHA is in the marker set, and does not stop a comment-triggered run whose head SHA is in the same set.
- The size gate is the only stop carrying a comment for the pull request.
- A pull request that passes every gate produces the head SHA and `proceed=true`.

**Errors and failures**

- A code fence left unclosed swallows the rest of the comment, so a `/coral` after it is inert.
- A tilde fence is not closed by a backtick fence, and a fence is not closed by a shorter run of its own character.
- A body with no lines at all, and a body that is only whitespace, are not requests.
- An association GitHub adds later is not write access and does not crash the parse.
- A pull request whose head repository is null is a fork rather than a `TypeError`.

**Edge cases**

- `/coral` inside a code fence that carries an info string, and one inside a fence indented up to three spaces.
- ``  `/coral` `` on its own line, `/coral` mid-sentence, `> /coral` as a quote, and `- /coral` as a list item, all inert.
- `/coral` indented by one space and by four, both inert.
- `/Coral` and `/CORAL`, both inert, which is the case the workflow's condition lets through.
- `/coral` followed on later lines by prose asking for something specific: a request, and the prose is conversation.
- A pull request exactly at 300 changed files and exactly at 30,000 changed lines passes; one line and one file past each stops.
- The head SHA in the marker set with the event being `pull_request` stops; the same state with the event being `issue_comment` proceeds.

**What NOT to test**

- That GitHub renders Markdown the way the parser reads it. The parser implements the fence rule and the live checks are what confirm the reading.
- Whether `viewerHasReacted` answers for the job's token. That is a live check, and no unit test can hold an opinion about it.
- `httpx` and the transport.

**Live checks**

All of these are in `kkestell/coral-test` and are read off the pull request.

1. Open a pull request and comment a body carrying `/coral` inside a code fence, mid-sentence, and quoted with a blockquote marker, and no live command anywhere. A run starts, because the job condition is coarse. No reaction appears, no review is posted, and the run is green.
2. Comment `/coral` alone on its own line, with prose on the lines around it. The comment gets the reaction and a review appears. This is the control for the check above.
3. Comment `/coral`, and while that run is going, comment `/coral` twice more in quick succession. The second run is queued and then cancelled by the third. All three comments carry the reaction, and two reviews appear. This is the reaction pass doing the thing the triggering payload cannot.
4. Reply `/coral` on the diff. That comment carries the reaction, which is the pulls namespace, and the reaction pass does not add a second one on a later run.
5. Close the pull request and comment `/coral`. The comment carries the reaction, the run declines because the pull request is closed, no review is posted, and the run is green.
6. Open a pull request ready for review and let Coral review it. Convert it to a draft and mark it ready again. The run starts, declines because the commit already carries a marker, and posts nothing. Then comment `/coral` on the same unchanged commit and get a review, which is the half of that gate that only applies to the automatic paths.
7. Open a pull request adding a generated file of more than 30,000 lines. Coral posts one comment saying the change exceeds what it will read, posts no review, and the run is green.
8. The fork gate needs a head branch in another account, so fork `kkestell/coral-test` into an organization or a second account, open a pull request from it, and comment `/coral`. The run declines because the head lives in a fork. Where no second account is available, this gate is covered by its unit test alone and the live check is recorded as not run.

## Implementation plan

1. **Write `coral/command.py`.** `asks_for_review(body)` walks the lines tracking fence state and returns whether any line outside a fence is exactly the command with trailing whitespace allowed. `is_request(body, association)` adds write access and the marker. The command, the fence pattern, and the association set are module-level `Final`. Comments say what the equality rule subsumes, so nobody adds a branch for blockquotes later, and why the case is exact when the workflow's condition is not.

2. **Carry the payload comment's body and association.** `coral/runner.py` reads `comment.body` and `comment.author_association` off the payload onto `Comment`, for both comment events.

3. **Ask the conversation query for the two new fields.** `databaseId` and `reactionGroups { content viewerHasReacted }` on all three fragments. `Comment` gains `database_id: int` and `reacted: bool`, which `PastReview` and `ThreadComment` inherit. One helper reads the eyes group out of the groups list. The comment beside it says the fields are on reviews because the dataclasses inherit and not because a review is ever a reaction target.

4. **Move the selection into `coral/github/reactions.py`.** A frozen `Request` carrying the REST id and the namespace, `requests_in(conversation)` returning the ones owed a reaction, and `react(github, owner, repo, requests)` posting to the namespace each one names. The module stops importing `coral/runner.py`, because it no longer knows what an event is.

5. **Add the plain comment to `coral/github/post.py`.** `post_comment(github, owner, repo, number, commit, body)` posting one issue comment carrying the marker. It sits beside `post_review` and shares `signed`.

6. **Write the gates in `coral/resolve.py`.** A frozen `Subject` holding the state, the head SHA, the two repository ids, the changed files, and the changed lines, and a function reducing the fetched pull request to it. A frozen `Decline` holding the reason and the comment the reason owes the pull request, which is `None` for four of the five gates. `declined(event, subject, conversation)` applying the five in order. The two size numbers are module-level `Final` with the comment saying they are chosen rather than measured and that item 9 settles them.

7. **Wire the step together.** Fetch the pull request, write it, fetch and bound the conversation, write it, react to the requests the conversation offers plus the one on the payload, then gate. A decline logs its reason, posts its comment when it has one, writes `proceed=false`, and returns. Otherwise the head SHA and `proceed=true` go out as before.

8. **Write `tests/test_command.py`** to the parser half of the test plan. This is the file the roadmap asks for, and the inert forms are one case each rather than one table, so a failure names the form that broke.

9. **Write `tests/test_resolve.py`** over `declined` and the reduction, building the `Subject`, the `Event`, and the `Conversation` directly.

10. **Write `tests/test_reactions.py`** over `requests_in`, building a conversation holding an issue comment that asks, a thread comment that asks, a review whose body asks, a request already carrying the reaction, a request from somebody without write access, and one of Coral's own comments.

11. **Update `tests/test_conversation.py`.** The captured response needs the two new fields, captured again from the same pull request rather than invented, and the assertions gain the fields they produce.

12. **Run the live checks** in order, and read each one off the pull request.

13. **Update the documents** listed below, and set the roadmap's item 4 status.

## Not doing

- **The agent, its environment, and the deadline.** Item 5. This item ends where the review step begins, and the review step still posts its hardcoded finding.
- **Rechecking the pull request's state before posting.** Item 7. That is the review step's recheck, and it is a different check from this item's gate: minutes pass in between, which is the whole reason both exist.
- **The failure comment and the report step.** Item 8. This item builds the transport that posts a plain comment and one caller for it. Nothing here reports a failure, and the size gate's comment is not one.
- **Settling 300 files, 30,000 lines, and the conversation bound.** Item 9, after real runs.
- **Reacting to a review body that carries the command.** GitHub has no endpoint for it, which is why asking that way is out of scope in the first place.
- **Telling an edited comment from a fresh one.** A comment edited to add `/coral` never triggers a run, because the workflow triggers on creation only. The reaction pass reads bodies as they are now, so such a comment can collect a reaction from a run somebody else started. The reaction says the comment was seen, a review is running regardless, and dropping every comment GitHub reports as edited would drop a request whose author fixed a typo.
- **Honoring a request whose run was cancelled by an inert one.** A comment that merely mentions `/coral` allocates a runner and can cancel a pending run, and its own run then stops at the inert gate without reviewing. The pending run's request is still acknowledged, because the reaction pass runs before the gates, but it gets no review until somebody asks again. Closing that would mean a run deciding to review on behalf of a request that is not its own, which needs a notion of an outstanding request that nothing in the design has.
- **Rate limiting or retrying the reactions.** One POST per owed request, on a pull request bounded to 200 comments. A failure takes the run down and item 8 reports it.
