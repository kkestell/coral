# What a review cost

Roadmap: item `16`, `What a review cost`.

Item 15 built the ledger: one `Ledger` crosses both agent runs, every OpenRouter response adds its own cost to it, and a review that reaches the cap stops. The number it holds is written to the log and nowhere a reader of the pull request can see it. This item puts it on the review.

The same change installs Coral on `kkestell/coral`, so the item is checked by a pull request on this repository rather than on the test repository.

## What Was Checked

- `coral/review.py` calls `payloads` after both agent runs return, so `ledger.spent` is final at that line. Nothing the publishing job does costs anything.
- `review_payload` composes both bodies — the anchored one and the one with every finding demoted — from the same function, so a figure added there lands on whichever body the publishing job posts.
- Every review measured against `kkestell/coral-test` cost a fraction of a cent; the account's `Coral` key spent $0.063 across all of them up to 2026-08-07.
- GitHub resolves `uses: ./.github/workflows/coral.yml` in the commit the calling file came from. On `pull_request` that is the pull request's own head, and on the comment paths it is the default branch, which is where GitHub reads the caller from.

## Goal

Every review ends with what the run spent. A pull request opened on `kkestell/coral` is reviewed by the Coral it changes.

## Approach

### The install

`.github/workflows/review.yml`, the caller file `examples/coral.yml` describes, differing in one line: it calls the workflow beside it rather than a pinned reference. The `OPENROUTER_API_KEY` secret is a plain API key rather than a management key, because this repository is public and its Actions logs are public with it — the one cleartext line a minted key crosses on would be readable by anybody until it expired.

### The figure

`cost(spent: float) -> str` in `coral/github/post.py`, rendering `*This review cost $0.0042.*`. Four decimal places, because two would print `$0.00` on every review measured so far.

`review_payload` and `payloads` take the amount and append that line last, after the findings and after whichever empty-outcome sentence applies. Last rather than beside the commit line: it is metadata about the run, and a reader should reach it after the review rather than ahead of the summary.

`coral/review.py` passes `ledger.spent` at the call that already logs it, so the body and the log carry the same number.

Nothing crosses a job boundary that did not already: the figure is inside the payloads the review job writes and the publishing job posts.

### Why not the schema

The amount is Coral's own accounting, not the model's. Putting it in `Review` would let a compromised agent understate what it spent, and the rule that deterministic code composes what Coral posts is what keeps that impossible.

## Out Of Scope

- The failure comment. A review that dies on its time budget spent money and reports none of it; the cap failure names its own total already, and the rest is a separate item if it is ever wanted.
- Any breakdown by agent run, by model, or by token count. One number.
