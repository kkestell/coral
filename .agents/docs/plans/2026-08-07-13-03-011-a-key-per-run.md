# A key per run

Roadmap: item `11`, `A key per run`.

## What Was Checked

Everything about OpenRouter below was measured on 2026-08-07 with the management key in `.env`, using a throwaway key minted with `limit: 0.10` and a three-minute `expires_at`, deleted afterwards.

- `POST /api/v1/keys` with `{"name": ..., "limit": 0.10, "expires_at": "2026-08-07T17:57:34.000Z"}` returns 201. The key string appears once, at the top level of the response under `key`, next to a `data` object carrying `hash`, `limit`, `expires_at`, and the usage fields. `expires_at` is echoed back exactly as sent — ISO 8601 UTC with milliseconds and a `Z` suffix.
- The provisioning docs page does not document `expires_at` at all; the field is real. Every key object in `GET /api/v1/keys` carries it, create accepts it, and it is enforced.
- Enforcement is at authentication time. The minted key completed against `openai/gpt-5.6-luna` 47 seconds before its `expires_at` and returned 401 `{"message": "User not found.", "code": 401}` on both `/api/v1/key` and `/api/v1/chat/completions` three minutes after it. No cleanup call was made in between.
- The management key cannot complete: the same completion request under it returns 401 `User not found.`. It can list, create, read, update, and delete keys under `/api/v1/keys`, and `DELETE /api/v1/keys/{hash}` answers `{"deleted": true}`.
- A minted key's `limit` is enforced per key: the test completion cost $0.0000039 and `limit_remaining` dropped by exactly that. The account's `Coral` key has spent $0.063 across every live check to date, so no single review has yet cost even a cent.
- The runner drops a job output whose value its secret masker would alter: `src/Runner.Worker/JobExtension.cs`, at the `Skip output '{name}' since it may contain secret.` warning, compares the output value against `SecretMasker.MaskSecrets`. The masker holds registered secrets *and* everything `::add-mask::` added. So a key masked in the job that mints it never crosses; the mask has to wait for the receiving job. The roadmap bullet saying "mask where it is created" was written against a wrong model of this and is corrected as part of this plan.
- `resolve()` in `coral/resolve.py` writes `proceed` and `head-sha` through `runner.write_output`; the composite action and the workflow map them upward. The channel item 10's plan promised for the minted key exists and a third output is one line at each of the three levels.
- `coral/review.py` pops `OPENROUTER_API_KEY` out of its environment before anything else and passes it down as a value; `coral/agent.py` wraps it in `SecretStr`. Neither knows where the key came from, so minting changes nothing in the review job's code.
- Publish already posts the failure comment with the reason when `reason.txt` crossed and without one when it did not, and it downloads artifacts by `pattern` into one merged directory. A `reason.txt` written by resolve would be read by the same code that reads one written by review.
- `actions/upload-artifact` warns only when *no* path matched, so adding `reason.txt` to resolve's upload list costs nothing on runs where it does not exist.
- Word counts: `architecture.md` 1,500 of 1,500 and `testing.md` 1,499 of 1,500 — both grow here, so both trim first. `development.md` 687 and `roadmap.md` 1,277 have room. `functional-requirements.md` 1,496 needs no change.

## Goal

The caller passes exactly one of two OpenRouter secrets. A plain API key flows to the review job as it does today. A management key never leaves the resolve job; resolve uses it to mint one key per run, capped by its own `limit` and dead at `expires_at` whether or not the rest of the run behaves. What an exfiltrated review-job key is worth falls from "the account's credit limit" to "a few dollars, for less than an hour."

## Approach

### Two secrets, one mode

`.github/workflows/coral.yml` declares both `workflow_call` secrets, each `required: false`:

```yaml
    secrets:
      openrouter_api_key:
        description: A plain OpenRouter API key, passed to the review job as it is.
        required: false
      openrouter_management_key:
        description: An OpenRouter management key. Coral mints one API key per run with it.
        required: false
```

The resolve action gains two inputs: `openrouter-management-key`, the secret itself, and `openrouter-api-key-present`, the string `${{ secrets.openrouter_api_key != '' }}`. Resolve needs to know the plain key exists, never its value, so the value stays out of a job that has no use for it.

`coral resolve` validates at the top, before the fetch: exactly one of the two must be set, and either zero or two is a `RuntimeError` naming both secrets and saying to set exactly one. Failing early makes a misconfigured install loud on every triggered run rather than only on the ones that pass the gates. Detection by probing is not built — the roadmap decided that, and `GET /api/v1/key` confirming a key's kind would cost a request to answer a question the caller already knows.

### Minting

`coral/openrouter.py`, a new module, the only place Coral speaks to OpenRouter's management API — the completions side stays where it is, behind `ChatOpenRouter` in `coral/agent.py`.

```python
KEY_LIMIT_DOLLARS: Final = 2.00
KEY_TTL_SECONDS: Final = 3600

def key_request(name: str, now: datetime) -> dict[str, Any]:
    """The create-key body: the name, the spend cap, and the expiry that revokes it."""

def minted_key(answer: dict[str, Any]) -> str:
    """The key string out of the create response, which carries it once and never again."""

def mint(management_key: str, name: str) -> str:
    """Create this run's API key. One `httpx` POST to `/api/v1/keys`."""
```

- `KEY_LIMIT_DOLLARS` is 2.00: two orders of magnitude above the most expensive review observed (under $0.01 — the account's `Coral` key has $0.063 of lifetime usage across every live check so far), and small enough that a leaked key is not worth the trouble of extracting. Re-measure when building and adjust the comment, not the reasoning.
- `KEY_TTL_SECONDS` is 3600: twice the review job's `timeout-minutes: 30`, the only long pole after minting, with the slack covering runner queue time between the jobs, which GitHub does not bound. A review job that starts too late finds its key expired, gets the provider's 401 in its lap, and the run goes red with that error in the failure comment — visible, rare, and fixed by asking again.
- `expires_at` is formatted the way the measurement sent it: ISO 8601 UTC, milliseconds, `Z` suffix.
- The key's `name` is the run URL from `runner.run_url()`. The OpenRouter dashboard then links every key it lists to the run that minted it, and a key that outlives its expiry mystery has its own audit trail.
- A non-201 answer raises with the status and body — OpenRouter's own words are what the failure comment should carry. No retry: one mint per run, and code style spends nothing on speculative robustness.

`resolve()` mints after the gates pass and before the outputs are written, so a failed mint fails the step before `proceed=true` exists. The validation and the mint are wrapped in a `try` that writes `described(error)` to `runner.reason_path()` and re-raises, the same shape as the review step's failure path: a broken management key or a rejected mint produces one comment carrying OpenRouter's own error, not "failed with no reason." `described` is imported from `coral/publish.py`. Resolve's upload gains `reason.txt` in its path list, and publish reads it exactly as it reads one the review job wrote.

### Crossing the boundary

Pass-through mode needs no channel: the review job's input reads the caller's secret directly. Minting mode crosses as a job output. The workflow's review job picks whichever exists:

```yaml
      - uses: $/actions/review
        with:
          coral-bin: ${{ steps.setup.outputs.bin }}
          openrouter-api-key: ${{ secrets.openrouter_api_key || needs.resolve.outputs.minted-key }}
```

The minted key is **not** masked in the resolve job. That is the measured constraint, not an oversight: the runner refuses to set a job output its masker would alter, and `::add-mask::` feeds that masker. The resolve job never logs the key — it goes from the HTTP response into `GITHUB_OUTPUT` and nowhere else, and job outputs appear in no log and no API. The review action's step masks it in the first line, before invoking Coral:

```yaml
      run: |
        set -euo pipefail
        echo "::add-mask::$OPENROUTER_API_KEY"
        "$CORAL_BIN/coral" review
```

Unconditional, because masking an already-masked registered secret is a no-op, so pass-through mode is unharmed.

One residue is accepted: with `ACTIONS_STEP_DEBUG` enabled, the runner's debug lines can print evaluated expressions in the receiving job before any step runs, and the minted key is not a registered secret there. Enabling debug logging is a maintainer's own act, the key answers to nobody but OpenRouter, and it dies at `expires_at` holding at most `KEY_LIMIT_DOLLARS`. Item 10 accepted the same class of residue for the job that holds the key legitimately.

### What does not change

- `coral/review.py`, `coral/agent.py`, `coral/environment.py`: the review job reads `OPENROUTER_API_KEY`, pops it, and uses it. Provenance is invisible.
- `coral/publish.py`: the reason file it reads may now have been written one job earlier; the reading is identical.
- The gates, the reaction, the conversation fetch, and both agent runs.

## Test plan

**Key behaviors to verify**

- `key_request`: `limit` is the constant, `expires_at` is `now` plus the TTL in the measured format, `name` passes through. Feed a fixed `datetime` and assert the exact string.
- `minted_key`: extracts the key from a trimmed real create response held inline; a response missing `key` raises with something a person can act on.
- Mode validation in `resolve`: four combinations — neither set, both set, API key only, management key only — where the first two raise naming both secrets and the last two proceed into their modes. Structure the check as a pure function over the two inputs so the test needs no environment.
- The reason file: a mint that raises leaves `described(error)` at `runner.reason_path()` — same pattern `tests/test_publish.py` already uses for reading it back.

**What NOT to test**

- `mint` end to end. It is one POST; the live checks and the local rehearsal below exercise it against the real API.
- Whether the `||` expression, the output mapping, or `add-mask` behave. That is Actions, not Coral, and it is what live check 2 shows.
- Expiry enforcement. Measured today by direct observation; re-measured any time with the rehearsal below. OpenRouter's clock is not unit-testable from here.

**Live checks**

Added as a group in `.agents/docs/testing.md`. The secret swaps happen in `kkestell/coral-test`'s Actions secrets and its caller file.

1. Pass-through, the control: with only `OPENROUTER_API_KEY` set and the caller passing only `openrouter_api_key`, open a pull request. The review appears exactly as it does today, green run.
2. Minting: remove that secret, set `OPENROUTER_MANAGEMENT_KEY`, point the caller at `openrouter_management_key`, open a pull request. A review appears, green run, no key material in any log. Under the management key, `GET /api/v1/keys` shows a key named with the run's URL, `limit` 2, `expires_at` one hour past the mint.
3. Expiry: the run's own key string is unrecoverable by design, so this check rehearses the same code path by hand — from a developer machine, mint through `coral/openrouter.py`'s own `mint` with a short TTL patched in, watch a completion succeed before `expires_at` and 401 after, then delete the key. This is the done condition's "no longer authenticates" made observable.
4. Misconfiguration: set both secrets and comment `/coral`. Red run, exactly one comment, and the comment says to set exactly one of the two. Then set the management key to a broken value with the API key absent: red run, one comment carrying OpenRouter's own error.

Check 3's local rehearsal needs `OPENROUTER_MANAGEMENT_KEY` in `.env`; the sourcing command is already under "Environment" in `.agents/docs/development.md`.

## Not doing

- **Deleting the minted key from the publish job.** Expiry already revokes without anyone's cooperation, which is why the roadmap chose it; a delete would put the management key into a second job and would be skipped by exactly the cancelled and killed runs that most need cleaning up after.
- **Detecting which kind of key one secret holds.** Decided against in the roadmap: a probe request to answer what the caller already knows.
- **Crossing the minted key as an artifact.** Artifacts on a public repository are downloadable by anyone with read access for their whole retention window. A job output is visible to no reader at all.
- **Encrypting the output so it could be masked at creation.** Machinery to defeat a runner check that is correctly protecting log hygiene, for a key that holds two dollars for one hour.
- **Retries, backoff, or a client class for one POST.** Code style: robustness against unobserved failures is not bought here.
- **`limitReset`, `include_byok_in_limit`, or per-repository management-key scoping.** The first two default correctly for a key that dies in an hour; the third does not exist on OpenRouter's side.
- **Validating the management key at install time.** The first triggered run validates it against the real endpoint and says so on the pull request.
