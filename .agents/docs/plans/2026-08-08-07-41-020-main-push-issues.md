# Main-push issues

Roadmap: item `20`, `Review main commits as issues`.

## Goal

Coral reviews each commit pushed to the default branch and creates one GitHub issue for every confirmed finding. Pull-request behavior stays unchanged: it still reads the pull-request conversation and posts one review.

## Decisions

- The push event is limited by the caller workflow to `main`. Coral still verifies the event's ref in Python, so a caller change cannot silently make another branch publish issues.
- The reviewed change is the pushed commit against its first parent. A root commit is declined because it has no prior repository state to compare.
- Main-push reviews receive no pull-request title, description, or conversation. Their request identifies the commit and says that no pull-request conversation exists.
- A confirmed finding creates one issue. The issue title contains the finding severity and the commit SHA. Its body contains Coral's marker, the commit SHA, the finding, its evidence, and the review's total cost.
- No finding creates no issue. A failed main-push run remains failed in Actions and creates no issue, because a failure is not a code finding.
- The event's `after` SHA is pinned in resolve and is the only ref review checks out. Publish does not re-fetch branch state: a later push is a different review and must not suppress the earlier commit's issues.

## Approach

Add `push` to the installed caller workflows, restricted to `main`. Its concurrency group uses the pushed SHA, so every main commit gets its own review and a later commit cannot replace a queued review. Keep the pull-request group unchanged.

Extend `runner.Event` with a main-push subject. Resolve receives the commit SHA and first parent from the event payload, validates the main ref, writes a small subject artifact, validates credentials and limits, and emits the checkout SHA. It does not fetch a pull request, conversation, collaborator permission, or reactions.

Change the review input from a pull-request payload to a review subject. The pull-request path continues to render the pull-request request and use the merge-base diff. The main-push path uses the parent diff and a request with no conversation. Both paths run the same reviewer and verifier.

Replace the review-only payload artifact with a tagged publish artifact. The pull-request variant keeps the existing two review bodies. The main-push variant holds one issue title and body per confirmed finding. The publishing job selects the variant from the event and uses `POST /repos/{owner}/{repo}/issues` for every main-push finding.

## Related code

- `coral/runner.py` — parse and represent a main-push delivery, and name the review subject artifact.
- `coral/resolve.py` — resolve either a pull request or a main-push commit.
- `coral/review.py` — render and review the parent diff without a pull-request conversation.
- `coral/github/post.py` — compose and post issue payloads.
- `coral/publish.py` — select review or issue publication.
- `.github/workflows/coral.yml`, `actions/resolve/action.yml`, `actions/publish/action.yml` — carry the extra subject data and upload it.
- `examples/coral.yml`, `.github/workflows/review.yml` — install the main-push trigger and safe concurrency groups.
- `tests/test_runner.py`, `tests/test_resolve.py`, `tests/test_review.py`, `tests/test_post.py`, `tests/test_publish.py` — cover the added pure behavior.

## Test plan

- A push delivery parses the pushed SHA, first parent, and ref. A non-main ref and a root commit are declined before minting a key.
- The main-push review request has the commit and parent diff but no pull-request conversation.
- Each finding renders to an issue title and body with its severity, anchor, evidence, commit marker, and cost. A review with no findings renders no issues.
- Publishing a main-push payload sends one issue request per finding. The pull-request publishing path remains a create-review request.
- Run `uv sync --frozen`, `uv run ruff format --check`, `uv run ruff check`, `uv run mypy`, and `uv run pytest`.
- Push a planted defect to `main` in `kkestell/coral-test`. Confirm a green run creates one issue per confirmed finding and no pull-request review. Revert the defect and close the created issues.

## Implementation plan

1. Add roadmap item 20 and update the documents that define this behavior.
2. Extend the event and resolve subject handling for main pushes.
3. Add main-push request rendering and issue payloads, then publish them.
4. Wire the reusable workflow and both caller workflows.
5. Add the unit tests and run the static checks and unit suite.
6. Run the live check before marking the roadmap item built.

## Not doing

- Deduplicating issues across commits. Coral has no datastore, and a finding that remains after a later commit needs a fresh issue for that commit.
- Updating or closing issues. Coral creates advisory findings and leaves issue lifecycle to maintainers.
- Reviewing non-main pushes or adding a per-repository mode switch. The caller's `on.push.branches` list is the configuration surface for this mode.
