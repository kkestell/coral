# A spend ceiling

Roadmap: item `15`, `A spend ceiling`.

Items 13 and 14 are built in the tree — the structured-output strategy is named in `coral/agent.py`, and the model, the effort, and the time budget are `workflow_call` inputs — while the roadmap still carries both as `not started`. This item builds on the shape item 14 left: one input, validated in resolve, driving a mint parameter.

## What Was Checked

Everything about OpenRouter below was read out of its live API on 2026-08-07; everything about `ChatOpenRouter`, DeepAgents, and LangChain out of the installed packages the same day.

- A chat completion's `usage` object carries `cost` with no `usage: {"include": true}` asked for. A `openai/gpt-5.4-nano` call returned `"cost": 2.015e-05` beside `cost_details` and `is_byok: false`, identically with and without the flag.
- `ChatOpenRouter` copies that number onto the message: `chat_models.py` sets `message.response_metadata["cost"]` from `usage["cost"]` on the non-streaming path and on the streaming path both.
- `POST /api/v1/keys` accepts a fractional-cent `limit`. A key minted with `"limit": 0.0001` came back carrying `limit: 0.0001` and `limit_remaining: 0.0001` exactly. The probe key was deleted.
- `langchain.agents.middleware.AgentMiddleware` offers `before_model` and `after_model` hooks, both taking the state and the runtime.
- `create_deep_agent` puts a summarization middleware in every agent's stack. It calls the model itself from its own `before_model`, keeps only `response.text`, and replaces the message list — so the AIMessage carrying that call's cost never reaches the state a middleware can read. A state-reading accumulator would silently miss it, and the calls it misses are the largest ones in the run.
- LangChain calls `on_llm_end` with the `LLMResult` whose generation holds that same mutated message, and the summarizer passes a `config` that carries only `metadata`, so the ambient callbacks reach its call too.

## Goal

The caller names one spend cap. It caps the minted key at mint time and stops a review whose own accounting reaches it, so the ceiling holds in both key modes. A review that stops says what it spent against the cap, in one comment, and posts nothing else.

## Approach

### The input

A fourth `workflow_call` input in `.github/workflows/coral.yml`, defaulted there and nowhere else: `spend_cap_dollars`, type `string`, default `"2.00"` — today's `KEY_LIMIT_DOLLARS`, so an existing install mints exactly the key it mints now.

`string` rather than the `number` the budget uses. The value reaches a composite action's `env:` block through the expression engine, which renders a number back into text on the way, and a cap of a fraction of a cent is where that rendering is not worth trusting. Coral parses text either way.

It travels the road item 14 built: an action input on `actions/resolve` and `actions/review`, then `CORAL_SPEND_CAP_DOLLARS` in each step's environment.

### Where the money lives

A new module, `coral/spend.py`, standing to money as `coral/deadline.py` stands to time: stdlib only, so it is testable without the agent framework, and the hooks that turn it into agent behavior live in `coral/agent.py` beside the framework they hook into.

- `cap_dollars(value: str) -> float` — parses and validates the input. A value that is not a number, is not finite, or is not above zero raises with the bound in the words, the way `budget_minutes` does. No upper bound: nothing outside Coral imposes one.
- `Ledger` — a mutable dataclass holding the cap and what has been spent, with `add` and `exceeded`. Mutable deliberately, and the one place in Coral that is: the reviewer and the verifier are two separate `invoke` calls with separate states, and one object crossing between them is what makes the cap cover the run rather than each run alone.
- `exceeded` is `spent >= cap`, matching `Deadline.expired`.

### The two hooks

Both in `coral/agent.py`, both holding the same `Ledger`:

- A `BaseCallbackHandler` subclass whose `on_llm_end` adds the response's `cost` to the ledger. A callback rather than a middleware hook, because it is the only place that sees the summarization middleware's own model call — the finding above. It reaches the run through `with_config`, beside the `recursion_limit` override already there.
- `SpendMiddleware`, whose `before_model` raises when the ledger is exceeded. The same shape as `DeadlineMiddleware` and for the same reason: the check is between steps, and the exception propagates out of `invoke` to the review step, which turns it into the comment. Its message names both numbers to six decimal places, because a cap of a fraction of a cent has to be legible.

A response carrying no `cost` counts as zero and logs a warning naming the model. Every OpenRouter completion measured carries one; a model that stops carrying one should say so in the log rather than end a review, and the minted key's cap is what the run still has under it.

### The two mechanisms meeting

`coral/openrouter.py` retires `KEY_LIMIT_DOLLARS`. `key_request` and `mint` take the cap as a parameter, and the mint log line names it.

`coral/resolve.py` validates the cap inside `reported(...)`, beside the budget validation and before the fetch, so a cap the caller got wrong is loud on every triggered run rather than only on the ones that reach a review. It hands the validated number to `mint`.

`coral/review.py` builds one `Ledger` from the same input and passes it to both agent runs, and logs the run's total when the review finishes. `produce_review` and `verify_findings` take the ledger the way they already take the deadline.

## Current state

- `KEY_LIMIT_DOLLARS = 2.00` in `coral/openrouter.py` is the whole of what bounds a run's spend, and only in minting mode. A passed-through key is bounded by whatever credit limit the caller set on it, which the README says.
- Nothing reads a response's cost. `DeadlineMiddleware` is the only thing that stops a run from inside the agent.
- The reusable workflow takes three inputs and two secrets.

## Test plan

**Key behaviors to verify**

- `spend.py`: `cap_dollars` accepts a plain decimal and rejects a non-number, a zero, a negative, and a non-finite value, each with the bound in the words; a ledger reports exceeded at exactly the cap and not below it; adding accumulates across calls.
- `agent.py`: the callback pulls the cost out of an `LLMResult` shaped like a real OpenRouter response; a response with no cost leaves the total alone; `SpendMiddleware` lets a model call through under the cap and raises at it, with both numbers in the message.
- `openrouter.py`: `key_request` carries the cap it was passed rather than a constant.
- `resolve.py`: an invalid cap fails inside `reported`, so the reason file is written; a proceeding run in minting mode mints at the cap it validated.

**What NOT to test**

- That OpenRouter enforces a key's limit, or that its reported cost is right. The live checks and the provider's own refusal cover both.
- Callback propagation into the summarization middleware. It is framework behavior, observable only in a run long enough to summarize.

**Live checks**

Added as a group in `.agents/docs/testing.md`. The cap swaps in `kkestell/coral-test`'s caller file, the secrets in its Actions secrets.

1. Pass-through mode, `spend_cap_dollars: "0.0005"`, on a change big enough to take several steps. Red run, exactly one comment naming what the review spent against the cap, and the same `RuntimeError` in the review step's log.
2. Minting mode, same cap. Red run, exactly one comment. It names either Coral's own total against the cap or OpenRouter's refusal of the key — both are the ceiling holding, and which fires depends on how far OpenRouter's usage accounting has caught up. `GET /api/v1/keys` shows the key minted at `0.0005`.
3. Remove the line. A review posts and nothing beside it, the log carries the run's total, and the minted key's limit is back to `2.00`.

## Not doing

- **A second input for the minted key's cap.** The roadmap decided one input drives both, and two would let the provider's cap and Coral's accounting disagree about the same run.
- **Stopping in `after_model`.** It would catch the call that crossed the cap rather than the one after it, at the price of throwing away a review that had just finished. The deadline already accepts one in-flight model request of overshoot, and this matches it.
- **Failing a response that carries no cost.** Named above: logged, counted as zero, backstopped by the provider's cap.
- **A per-run budget split between the reviewer and the verifier.** Time is split because the verifier needs a guarantee of some; money is a single pool, and a reviewer that spends it all leaves a run with nothing to verify and a comment saying so.
- **Reading the key's usage back from OpenRouter mid-run.** A request per step to learn a number every response already carries.
- **An upper bound on the cap.** GitHub's job ceiling is what bounds the budget; nothing outside Coral bounds a dollar figure.
- **`Decimal`.** Costs arrive as JSON floats and are summed a few dozen times per run; the error is nowhere near a cent.
