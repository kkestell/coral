# Walking Skeleton

Roadmap: item `2`, `Walking skeleton`.

## Research

- `.agents/docs/research/reusable-workflow-packaging.md` — that `$/` resolves against the repository holding the file it appears in, that a composite action cannot read the `secrets` context, and that a called workflow's `permissions` block filters rather than grants.
- `.agents/docs/research/github-api-contract.md` — the permission set each reaction endpoint requires, the seven fields a batched review's comment entries accept, and that an omitted `event` creates a review nobody can read.
- `.agents/docs/research/code-structure.md` — the composite-steps arrangement, where state crosses a step boundary as a path on disk, and the projects that write their step outputs from inside the library rather than from the wrapper.

## Goal

Get one run of the whole workflow to happen, with no model call anywhere in it.

The deliverable is a pull request in `kkestell/coral-test` carrying a review from Coral, produced by a workflow that repository installed by adding one file. The review's summary is hardcoded and its single finding is hardcoded, anchored to a line Coral picked out of a diff it computed itself. Everything between the trigger and the posted review is the real thing: the reusable workflow, the composite actions, the `$/` references between them, the environment Coral installs itself into, the reaction, the sentinel, and the batched review.

Satisfies TR-4, TR-15, TR-16, TR-27, TR-28, TR-36, TR-46, TR-49, and TR-51, and gives FR-1, FR-5, FR-9, FR-11, FR-25, FR-26, and FR-27 their first real path. The roadmap's done condition is a review on a pull request in the second repository, posted by a workflow installed with one file.

Four things can only be learned from a run, and this item exists to learn them.

- Whether `issues: write` and `pull-requests: write` together actually reach the two reaction endpoints from inside a job.
- Whether the `$/` reference resolves on a GitHub-hosted runner.
- Whether a batched review with `event: COMMENT` posts and is visible to somebody other than its author.
- How state crosses a step boundary in practice: a commit SHA as a step output, the pull request as a file under the runner's temporary directory, and a decline as an output rather than as a failed step.

## Approach

### Five steps, and this item builds four of them

The run is `setup`, `resolve`, `checkout`, `review`, `report`. The report step is roadmap item 8 and nothing here builds it.

The setup step is new, and it exists because Coral's own virtual environment has to be built exactly once and used on both sides of the checkout. It installs `uv`, runs `uv sync --frozen` into a virtual environment under `RUNNER_TEMP`, and publishes the directory holding the console script as a step output. Resolve and review take that directory as an input and run `"$CORAL_BIN/coral"` by absolute path.

Invoking by absolute path is what makes TR-42 cheap. Coral's virtual environment is never placed on `PATH` and is never activated, so `PATH`, `VIRTUAL_ENV`, and the `UV_*` variables in the review step's own process are exactly what the runner set. The filter TR-42 describes stays in the code as a belt, and item 5 writes it, but it has nothing to remove.

The alternative — resolve builds the environment and review finds it at an agreed path — was rejected. It puts environment construction inside the gatekeeper, so the log line saying why a run stopped sits underneath a dependency install, and the coupling between the two actions becomes a convention nothing checks.

### What crosses a step boundary

Two things cross as step outputs, and both are read by YAML rather than by Python. `head-sha` is what the checkout step needs. `proceed` is how resolve stops the run.

A decline is not a failure. Resolve writes `proceed=false`, prints its reason, and exits zero, and the checkout and review steps carry `if: steps.resolve.outputs.proceed == 'true'`. A run that Coral declined is a green run with two skipped steps, because a pull request Coral was never going to review is not a broken pull request.

Everything else crosses as a file. Resolve writes the pull request exactly as the API returned it to `$RUNNER_TEMP/coral/pull-request.json`, and review reads the head SHA, the base SHA, the number, and the repository back out of it. That is the same mechanism TR-34 needs for the conversation in item 3, exercised now, on something item 2 has anyway. It also means neither commit is fetched twice, which is what FR-11 rests on.

### The one home for the runner

`coral/runner.py` is new, and TR-10 is what asks for it: reading the event payload, writing step outputs, and finding the runner's temporary directory are needed by more than one subcommand and belong in one place. It also becomes the single home for `GITHUB_WORKSPACE`, so there is one answer to where the checkout lives.

Every value it reads comes out of `os.environ` by subscript. A missing `GITHUB_EVENT_PATH` is a broken invocation, not an input to recover from, and a `KeyError` naming the variable is the clearest thing that can happen.

### Coral's own code runs git, and the agent does not

`coral/diff.py` runs `git merge-base` and `git diff` inside the checkout. TR-41 as currently written forbids that, and TR-41 is wrong rather than the design: what it means to say is that the *agent* reaches the checkout only through the backend. Deterministic code computing the diff of TR-47 is not agent access. The requirement is corrected below.

The diff is split so the interesting half is testable without a repository. `parse_added_lines` takes the text `git diff` produced and returns the lines that are in the diff on the new side. `added_lines` runs git and calls it. Item 7 validates anchors against exactly this function.

### The reaction, narrowed to what this item can prove

TR-27 wants a reaction on every qualifying request in the conversation. Reading the conversation is item 3 and recognizing a command is item 4, so this item reacts to the one comment on the triggering payload and nothing else. That is enough to answer the permission question, because the two comment events land in different namespaces: `issue_comment` reacts through `/repos/{owner}/{repo}/issues/comments/{id}/reactions` and `pull_request_review_comment` through `/repos/{owner}/{repo}/pulls/comments/{id}/reactions`. Item 4 changes which comments get reacted to and not how.

### One gate, so the skip path is real

None of the gates in TR-30 is built here; they are item 4. One exception: resolve stops when the pull request is closed or merged. It is three lines, the field is already on the response, and it is the only gate that can be exercised live in `kkestell/coral-test` without a second account or a fork. Without it, `proceed` is a mechanism that has never once been false.

## Test plan

Everything that can be decided without the network is a unit test. Everything else is one live run against `kkestell/coral-test`, and the evidence is what ends up on the pull request.

**Key behaviors to verify**

- `parse_added_lines` returns one entry per line added on the new side, with the path and the 1-based line number, given the text `git diff --unified=0` produces for a change touching two files.
- `runner.event()` reads the pull request number from `pull_request.number` on a `pull_request` payload, from `issue.number` on an `issue_comment` payload, and from `pull_request.number` on a `pull_request_review_comment` payload, and reports the comment's namespace as `issues` for the second and `pulls` for the third.
- `runner.write_output` appends `name=value` to the file named by `GITHUB_OUTPUT` and leaves what was already in it alone.
- `marker.marker(sha)` and `marker.reviewed_commit(body)` round-trip a SHA through a review body whose first line is the sentinel.

**Errors and failures**

- `runner.event()` raises `KeyError` naming the variable when `GITHUB_EVENT_PATH` is unset, rather than returning a half-built event.
- `runner.write_output` raises `AssertionError` on a value containing a newline. Every value this item writes is a SHA or a boolean, so the heredoc form in the Actions protocol is not built; the assertion is what stops a later caller assuming it was.
- `marker.reviewed_commit` returns `None` for a body with no sentinel in it, which is what item 3 reads as "somebody else wrote this".

**Edge cases**

- A hunk header with no count, `@@ -1 +1 @@`, means one line, not zero.
- A hunk header whose new-side count is zero, `@@ -4,3 +3,0 @@`, is a pure deletion and contributes no lines.
- A file whose new side is `/dev/null` was deleted and contributes no lines.
- A newly added file contributes every one of its lines.
- A path containing a space survives, which is why git is run with `core.quotePath=false`.
- A diff with no added lines anywhere produces an empty list, which is the case review has to handle by anchoring its finding to the pull request instead of to a line.

**What NOT to test**

- `httpx`, the GitHub API, and the shape of an API response. A test that asserts what GitHub returns is a test of a fixture somebody wrote down.
- The composite actions and the reusable workflow. There is no way to run these except by running them, which is what the live checks below are.
- That `git diff` produces the format the parser reads. The parser is tested against captured output; whether git still produces it is what the live run finds out.

**Live checks, in `kkestell/coral-test`**

Each one is a real pull request and its evidence is on that pull request.

1. Open a pull request that changes one file. A review from Coral appears, carrying one inline comment on a changed line and a summary naming the commit. This is the done condition.
2. Comment `/coral` on that pull request. The comment gets the `eyes` reaction and a second review appears. This is the issues-namespace reaction and the `pull-requests: write` plus `issues: write` question.
3. Reply `/coral` on the diff. That comment gets the `eyes` reaction and a third review appears. This is the pulls-namespace reaction.
4. Close a pull request and comment `/coral` on it. The run starts, resolve declines, the checkout and review steps are skipped, no review is posted, and the run is green.
5. Open a pull request as a draft. No job runs at all, because the job-level condition rejects it before a runner is allocated.

## Implementation plan

1. **Write `coral/runner.py`.** Frozen dataclasses `Comment`, carrying `id: int` and `namespace: Literal["issues", "pulls"]`, and `Event`, carrying `name: str`, `owner: str`, `repo: str`, `number: int`, and `comment: Comment | None`. `event()` reads `GITHUB_EVENT_NAME`, splits `GITHUB_REPOSITORY` on the slash, loads the JSON at `GITHUB_EVENT_PATH`, and matches on the event name for the number and the comment: `pull_request` takes `pull_request.number` and has no comment, `issue_comment` takes `issue.number` and a comment in the issues namespace, `pull_request_review_comment` takes `pull_request.number` and a comment in the pulls namespace. Any other name is an `AssertionError`, because the workflow's `on:` block is the only thing that can produce one. Then `write_output(name, value)` appending to `GITHUB_OUTPUT` after asserting the value holds no newline, `temporary_directory()` returning `$RUNNER_TEMP/coral` and creating it, and `workspace()` returning `GITHUB_WORKSPACE` as a `Path`.

2. **Write `coral/github/client.py`.** A frozen dataclass `GitHub` holding `token: str`, with `get(path)` and `post(path, body)` returning parsed JSON. Base URL, the `Accept: application/vnd.github+json` header, the `X-GitHub-Api-Version: 2022-11-28` header, and the bearer token go in one place. On a non-success status, raise `RuntimeError` carrying the method, the path, the status, and the response body — not `raise_for_status()`, which drops the body, and the body is the whole of what item 7 needs from a 422 and what item 8 turns into a comment. Create `coral/github/__init__.py` in this task, empty.

3. **Write `coral/github/reactions.py`.** One function, `react(github, event)`, that does nothing when the event carries no comment and otherwise posts `{"content": "eyes"}` to the endpoint its namespace names. Two `match` arms, no branching anywhere else. Record in a comment that posting the same reaction twice returns 200 rather than creating a second one, so nothing here needs to read first; TR-27's "does not already carry one" becomes real in item 4, when there is a conversation to scan.

4. **Write `coral/github/marker.py`.** A module-level `Final` sentinel and two functions. `marker(commit)` returns `<!-- coral:reviewed commit={commit} -->`. `reviewed_commit(body)` matches that shape anywhere in a body and returns the SHA or `None`. The writer is what this item needs; the reader is written now because the format is decided now and a round-trip test is what pins it, and item 3 is its first caller.

5. **Write `coral/diff.py`.** A frozen `AddedLine` carrying `path: str` and `line: int`. `parse_added_lines(text)` walks the diff text, tracking the current path from each `+++ b/<path>` line and skipping `+++ /dev/null`, and for each `@@ -a,b +c,d @@` yields lines `c` through `c + d - 1`, treating a missing count as 1 and a count of 0 as nothing. `added_lines(workspace, first, second)` runs `git -c core.quotePath=false diff --unified=0 --no-color --no-ext-diff <first> <second>` with `cwd=workspace` and `check=True`, and hands the output to the parser. `merge_base(workspace, base, head)` runs `git merge-base` and returns the SHA. Both git functions go through one small helper so there is one place that knows a subprocess is involved.

6. **Write `coral/resolve.py` and point the CLI at it.** Read the event. Read `GITHUB_TOKEN` from the environment. Fetch `GET /repos/{owner}/{repo}/pulls/{number}`. React to the triggering comment. Write the response verbatim to `pull-request.json` under the temporary directory. When `state` is not `open`, log the reason to stderr, write `proceed=false`, and return. Otherwise write `head-sha` from `head.sha` and `proceed=true`. The order matters and is worth a comment: the reaction is FR-9's acknowledgment and comes before any decision that could stop the run, because a request Coral is going to decline for being closed still deserves to be told it was heard.

7. **Write `coral/review.py` and point the CLI at it.** Pop `GITHUB_TOKEN` out of `os.environ` rather than reading it, which is the shape TR-14 asks for and which item 5 extends to the OpenRouter key. Read `pull-request.json`. Compute the merge base of `base.sha` and `head.sha` and then the added lines. Build the review in one function named so item 5 knows where the agent goes — a summary saying this run made no model call, and one finding anchored to the first added line, or to the pull request when there are none. Post it.

8. **Write `coral/github/post.py`.** `post_review(github, owner, repo, number, commit, review)` builds the body as the marker, then a line naming Coral and the commit it reviewed, then the summary, then any demoted findings. It maps the findings with an exhaustive `match` over the four anchors: a span becomes a comment with `start_line`, `line`, and `side: "RIGHT"`, a line becomes a comment with `line` and `side: "RIGHT"`, and a file anchor and a pull request anchor go into the body, the first naming its file. That demotion is TR-49 and is by construction rather than by failure. Post one `POST /repos/{owner}/{repo}/pulls/{number}/reviews` with `commit_id`, `body`, `comments`, and `event: "COMMENT"` — the event named explicitly, because omitting it creates a review in the pending state that nobody but its author can read. Anchor validation against the diff, the demotion that follows from it, the retry on a rejection, and the state recheck are all item 7.

9. **Write `actions/setup/action.yml`.** A composite action with one output, `bin`. Two steps: `astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0`, then a bash step under `set -euo pipefail` that resolves Coral's own root as `${GITHUB_ACTION_PATH}/../..`, sets `UV_PROJECT_ENVIRONMENT` to `${RUNNER_TEMP}/coral-venv`, runs `uv sync --frozen --project "$coral_root"`, and writes `bin=${RUNNER_TEMP}/coral-venv/bin` to `GITHUB_OUTPUT`. The action directory is where the runner unpacked Coral's repository, so `../..` from it is the tree holding `pyproject.toml`, `uv.lock`, and `.python-version`. `uv` reads that last file and installs the interpreter itself, so no `setup-python` step exists.

10. **Write `actions/resolve/action.yml` and `actions/review/action.yml`.** Each declares `coral-bin` and `github-token` as required inputs, and review also declares `openrouter-api-key`. Each has one bash step that puts its inputs on the step's `env:` and runs `"$CORAL_BIN/coral" resolve` or `"$CORAL_BIN/coral" review` — the values reach the shell as environment variables rather than being interpolated into the script, so nothing in an input is ever parsed as shell. Resolve declares `proceed` and `head-sha` as outputs, forwarded from its run step, which is where `coral resolve` wrote them.

11. **Write `.github/workflows/coral.yml`.** `on: workflow_call` with one declared secret, `openrouter_api_key`, `required: false` while there is no model call; item 5 makes it required. One job, `runs-on: ubuntu-latest`, `timeout-minutes: 30` per TR-54, and a `permissions:` block naming `contents: read`, `issues: write`, and `pull-requests: write` — a filter rather than a grant, which documents the requirement and narrows a caller who granted more. The job-level `if:` is TR-21's coarse condition, as three alternatives joined by `||`: a `pull_request` that is not a draft and whose author's `type` is not `Bot`; an `issue_comment` whose issue carries a `pull_request` key, whose body contains `/coral`, and whose `author_association` is in `["OWNER", "MEMBER", "COLLABORATOR"]`; and a `pull_request_review_comment` with the same body and association tests. The steps are the four of them, `$/actions/setup`, `$/actions/resolve`, `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` with `ref`, `fetch-depth: 0`, and `persist-credentials: false`, and `$/actions/review`, with the last two carrying `if: steps.resolve.outputs.proceed == 'true'`.

12. **Write `examples/coral.yml`,** the file a repository adds to install Coral. It carries the five things TR-4 says it has to carry and nothing else: the `on:` block naming the three events and their types, a workflow-level `concurrency` group keyed on `github.event.pull_request.number || github.event.issue.number` with `cancel-in-progress: false`, a `permissions:` block on the calling job, `uses: kkestell/coral/.github/workflows/coral.yml@main`, and `secrets: openrouter_api_key: ${{ secrets.OPENROUTER_API_KEY }}`. The concurrency group is declared only here and never in the called workflow, because a group shared between caller and called cancels the caller.

13. **Write the unit tests** to the test plan: `tests/test_diff.py`, `tests/test_runner.py`, and `tests/test_marker.py`. The runner tests write an event payload into `tmp_path` and point the environment at it with `monkeypatch`, which is the runner's own protocol rather than a fake of Coral's code. The diff tests hold captured `git diff` output inline.

14. **Install Coral into `kkestell/coral-test`.** Push `examples/coral.yml` to that repository as `.github/workflows/coral.yml`, on its default branch, because the comment paths always read the workflow from there. Then run the five live checks above, in order.

15. **Update the documents** listed below, and set the roadmap's item 2 status.

The setup step installs `uv` and builds Coral's own virtual environment under the runner's temporary directory, publishing the directory holding the console script, because resolve runs before the checkout and review runs after it and the environment can only be built once.
