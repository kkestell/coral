# Technical Requirements

THIS FILE MUST BE KEPT UP TO DATE AT ALL TIMES

How Coral is built and what it is built on. What Coral does is in `.agents/docs/functional-requirements.md`.

Every limit quoted here is a real platform limit that the design has to live inside. Where a decision is still open, it is listed under "Undecided" rather than guessed at. Numbers that were chosen rather than measured say so where they appear.

## Platform

- **TR-1** — Coral is a GitHub Actions workflow. There is no cloud account, no infrastructure to provision, and no service standing by between reviews. GitHub supplies the trigger, the compute, the checkout, and the credential, and Coral supplies the review.
- **TR-2** — Coral is written in Python. Dependencies are managed with `uv` against a committed lockfile and installed on the runner with `uv sync --frozen`. Nothing resolves versions at run time.
- **TR-3** — Coral ships as composite actions in its own repository, wired together by a reusable workflow, and installed by a short file in each repository that calls that workflow. That per-repository file carries five things, and it has to carry all five: the version pin, the OpenRouter secret, the `on:` block naming the events in TR-16, the `permissions:` block in TR-11, and the concurrency group in TR-21. A reusable workflow cannot declare its caller's triggers and cannot grant itself permissions the caller withheld, so those three cannot move upstream. What drifts between repositories is therefore a tag plus a small block of boilerplate, and the boilerplate is worth keeping identical. If Coral's own repository is private, calling repositories reach the reusable workflow only when the organization has enabled that access.
- **TR-4** — There is no way to skip the per-repository file. An Enterprise Cloud organization can push a workflow across its repositories through a ruleset, but a ruleset workflow runs only on `pull_request`, `pull_request_target`, and `merge_group`, so it could never carry the comment triggers FR-5 needs. It is also a merge gate rather than a trigger, which would make a Coral outage block merges across the organization and contradicts FR-30 outright.
- **TR-5** — The review agent is built with DeepAgents.
- **TR-6** — Models are reached through OpenRouter, using the `langchain-openrouter` package and its `ChatOpenRouter` chat model. No model provider is called directly.
- **TR-7** — The model is `~deepseek/deepseek-v4-flash-latest`. It offers a 1,048,576-token context window and supports tool calling, structured outputs, and a reasoning effort setting, which are the capabilities the rest of this document depends on. The leading tilde is an OpenRouter alias resolving to the newest release in the DeepSeek V4 Flash family, so the model behind it changes without notice.
- **TR-8** — Coral owns no datastore. Everything Coral needs to remember about a pull request is already written on that pull request, by requirements Coral has to satisfy anyway, and Coral reads it back at the start of every run. This is the decision the rest of the design hangs off. TR-29 is what makes it possible, and FR-14 is what spends it.

## What The Agent Can Reach

The agent runs shell commands inside a checkout of the repository under review, and that repository's own code runs in the same place.

- **TR-9** — The agent's only return value is a structured review object, and deterministic code does the posting. There is no output the model can produce that becomes a push, an approval, or a comment Coral did not compose. This constrains what the agent hands back. It does not by itself constrain what the agent's shell does, which is why FR-20 and FR-30 need TR-10 as well.
- **TR-10** — Both secrets are removed from the environment the agent's shell inherits. The review step reads the OpenRouter key and the GitHub token out of its environment at start-up, holds them in memory, deletes them from `os.environ`, and only then constructs the model client and the backend. Nothing passes them to a child process afterwards. The chat model holds the key it was handed and the posting code holds the token it was handed, so both still work, and a shell command that reads the environment finds neither. Without this, an agent with `pull-requests: write` in its environment could submit an approving review with one `curl`, and FR-30 would be a request rather than a property.
- **TR-11** — The job's token is scoped by a `permissions` block naming `pull-requests: write` and `contents: read`, and nothing else. It expires when the job ends. There is no key to store, nothing to mint, and nothing to rotate, which is the largest single saving of running inside Actions.
- **TR-12** — The checkout is taken with `persist-credentials: false`. The default writes the token into the repository's own git config as an HTTP header, where the agent would find it by reading a file. Turning it off is one input, and skipping it would hand back what TR-10 and TR-11 just bought.
- **TR-13** — This is not a sandbox, and nothing in the design should be written as though it were. The agent runs arbitrary shell commands as the runner user, with network access, and can read any file on the runner. TR-10 is a barrier rather than a boundary: it puts the secrets out of easy reach, and it does not stop a determined agent from going looking elsewhere on the runner. What makes the remaining exposure acceptable is that Coral is the repository's own continuous integration, running the repository's own code on the repository's own runner.
- **TR-14** — The pull request conversation is untrusted input, and it is untrusted in a way the repository's own contents are not. Anyone who can comment can write into it, including someone with no access to the repository at all, and what they write reaches a model that holds an unsandboxed shell. The write-access check in TR-18 decides who can start a run. It does not decide whose text the agent reads, and FR-14 requires the agent to read all of it. So the reachable attack is this: a stranger leaves a comment, a maintainer later asks for a review, and the stranger's text is in the agent's context while the agent has a shell. FR-16 states the behavior Coral wants and it is a prompt-level defense, not an enforced one. What actually bounds the damage is TR-10, which keeps the secrets out of the shell's environment, and TR-9 together with FR-30, which keep anything the agent is talked into from becoming a change to the repository or the merge. The residual risk is command execution on a throwaway runner holding a checkout of code that is already public to everyone who can see the pull request. That is accepted for a proof of concept and is the first thing to revisit if Coral is run anywhere that matters.
- **TR-15** — Every comment handed to the agent is labeled with its author's association, so the difference between an owner and a drive-by account is visible in the input rather than inferred from tone. This does not enforce FR-16 and is not claimed to. It is the cheapest thing that gives the model any basis at all for the judgment FR-16 asks of it.

## Triggering

- **TR-16** — The workflow triggers on the `opened` and `ready_for_review` types of `pull_request`, and on the `created` type of both `issue_comment` and `pull_request_review_comment`. It does not trigger on `synchronize`. GitHub sends `issue_comment` for a comment on a pull request as a whole and `pull_request_review_comment` for one on the diff, which is why FR-5 needs both. It does not trigger on `pull_request_review`, because GitHub has no endpoint for reacting to a review — reactions exist for issues, issue comments, review comments, commit comments, and releases, and not for the review object — so a request arriving that way could never be acknowledged under FR-9.
- **TR-17** — A job-level condition rejects deliveries that are certainly not triggers, before a runner is allocated. It is a coarse filter and cannot be anything else: Actions expressions offer `contains`, `startsWith`, and `endsWith`, with no regular expressions and no way to work line by line. So on the comment paths the condition tests that the body contains `/coral` at all, that the comment sits on a pull request rather than an issue, and that the author association passes TR-18. The exact recognition FR-6 describes — alone on its own line, not quoted, not inside a code fence — needs a real parse of the comment body and happens in the resolve step, which stops the run when the command is inert. The cost is that a comment merely mentioning Coral allocates a runner and then stops within seconds. On the `pull_request` path the condition also covers the two exclusions in FR-2, read from `draft` and from the author's `type` on the payload. A `type` of `Bot` catches GitHub Apps such as Dependabot, and does not catch a script driving an ordinary user account, which is as far as a payload field can take it. The bot exclusion is deliberately not applied on the comment paths: a bot that has write access and types `/coral` is asking on somebody's behalf, and FR-2's reasoning about volume does not apply to a command somebody had to write.
- **TR-18** — `issue_comment` fires for comments on plain issues as well as on pull requests, and the two are told apart only by the `pull_request` key on the issue object. The condition checks for it. An issue number is not a pull request number.
- **TR-19** — Write access is read off the `author_association` field on the comment payload, where `OWNER`, `MEMBER`, and `COLLABORATOR` count as write access. It is already in the payload, so the check FR-8 asks for costs no API call. It is broader than write access in two directions. `MEMBER` means the author belongs to the organization that owns the repository, which does not by itself grant write access to that repository. `COLLABORATOR` means the author was invited to collaborate, which includes an outside collaborator invited with read-only permission. Both are accepted. Narrowing either means a permissions call on every comment, and the population let through is people somebody deliberately added to the repository or the organization.
- **TR-20** — Coral cannot trigger itself, and this costs nothing to arrange. Events created with the job's own `GITHUB_TOKEN` do not create workflow runs at all, excepting only `workflow_dispatch` and `repository_dispatch`. FR-7 is therefore a property of the platform rather than a rule Coral has to keep. It stops being free the moment Coral is given an identity of its own, so any future move to a GitHub App has to bring an explicit self-check with it.
- **TR-21** — The fork check in FR-3 is a security control on the comment path, not a statement of scope. A comment event fires in the base repository, so a `/coral` on a pull request from a fork would run with the base repository's token and the base repository's secrets, against a branch nobody with write access has vouched for. The resolve step reads the head repository off the pull request and stops when it differs from the base, treating a deleted head repository as a fork. On the `pull_request` path GitHub already withholds secrets and downgrades the token for forks, so the job could not work even if it ran, but Coral filters there too rather than relying on a failure to be the guard.
- **TR-22** — Concurrency is a group keyed on the pull request number, with `cancel-in-progress` left false. A run already in progress finishes, and a newly queued run cancels whichever run was pending in that group. That gives FR-33 its collapse behavior on this platform as a key in the workflow file rather than a coordination protocol. The number is read from `pull_request.number` or `issue.number` depending on which event fired, and the two cannot collide because GitHub numbers issues and pull requests from one sequence.
- **TR-23** — The reaction FR-9 promises is left by the resolve step, as soon as the request is accepted and before the review begins. A comment-triggered run does not appear among the pull request's checks, so the reaction is the only sign the person who asked will get until the review lands. Because TR-22 collapses pending runs, the request that started this run is not necessarily the only one waiting on it. The resolve step is already reading the conversation, so it reacts to every `/coral` comment that qualifies under FR-6 and FR-8 and does not already carry Coral's reaction, not only to the one on the triggering payload. That is what keeps FR-9 true for a request whose own run was cancelled before it started.

## Running The Review

- **TR-24** — The workflow runs four steps in a fixed order: resolve, check out, review, and report. The first three carry the work, and the order is what the rest of this section depends on. The split between resolve and checkout exists because the checkout needs a commit SHA that only an API call can supply. The report step exists for TR-55 and runs only on failure.
- **TR-25** — The resolve step asks GitHub for the pull request and reads the head SHA, the base branch's current SHA, the state, the draft flag, and the head repository off the answer. Both SHAs are pinned here and neither is read again. The head SHA is the subject of the review per FR-10, and pinning the base as well is what makes FR-11 true: the merge base is computed from two fixed commits, so the diff Coral reviews cannot shift underneath it when either branch moves during the run.
- **TR-26** — The resolve step also fetches the conversation, decides whether there is a review to do at all, and stops the run when there is not. It stops when the command is inert under FR-6, when the pull request is closed, when the head belongs to a fork, when the change exceeds TR-31, and, on the two automatic paths only, when this commit has already been reviewed. Each stop comes before the work it would make pointless.
- **TR-27** — The conversation is fetched with GraphQL rather than REST, in one query, because FR-14 needs to know whether a past finding still stands and that means reading each review thread's `isResolved` and `isOutdated` fields. REST does not expose either. The query returns the pull request's reviews, its review threads with their comments, and its issue comments, each with its author and author association.
- **TR-28** — The conversation is bounded at the 200 most recent comments and 400,000 characters, whichever binds first, and the review says what was dropped when either does, which is what FR-15 asks for. Both numbers are chosen rather than measured. TR-31 bounds the diff and this bounds the discussion, and without it a long-lived pull request would silently spend the context window on argument rather than on code.
- **TR-29** — The conversation is also the answer to whether this commit has already been reviewed, which is what lets TR-8 stand. Every review Coral posts opens with an HTML comment carrying a fixed sentinel and the reviewed commit SHA, invisible in rendered Markdown and exact to match. That marker is how Coral recognizes its own past work, and reading the SHAs out of it gives the set of commits Coral has looked at, written in a place GitHub maintains for free. The prose in FR-26 and FR-27 is for the human reader; the marker is for the next run, and neither substitutes for the other. The already-reviewed check applies to the two automatic entry points in FR-1 only, where it stops a pull request that is opened ready, converted to draft, and marked ready again from being reviewed twice at the same commit. A request under FR-5 never tests the head, because somebody who asks gets a review whether or not the code has moved.
- **TR-30** — The conversation is written to the runner's temporary directory rather than passed between steps as an output. It is too large to be an output, and the temporary directory is outside the workspace, so the checkout in TR-32 does not disturb it. This is what keeps the conversation fetched once rather than twice.
- **TR-31** — The resolve step stops when the change exceeds the bound FR-37 sets, before the clone. The bound is 300 changed files or 30,000 changed lines, and `changed_files`, `additions`, and `deletions` all come back on the pull request fetch in TR-25, so the check costs no call of its own. Both numbers are chosen rather than measured, and both are backstops set well above anything a person opens by hand, so they are not expected to be tuned.
- **TR-32** — The checkout takes the head SHA the resolve step produced, with `fetch-depth: 0` and the `persist-credentials: false` of TR-12. Full history is what makes the merge base exact, which FR-11 needs and which no shallow depth can promise, and it also brings the base SHA into the clone: `fetch-depth: 0` fetches `+refs/heads/*:refs/remotes/origin/*`, so every branch head is present locally. Checking out the resolved SHA rather than the branch matters because the branch may have moved since TR-25 read it. When it has moved by force-push the SHA can be unreachable and the checkout fails outright, which is one of the cases TR-55 exists to report.
- **TR-33** — The review step passes the conversation to the agent as part of its input, which is what FR-14 needs, and constructs the agent only after the working tree exists and after the secrets have been stripped per TR-10. Setup is not the agent's job.
- **TR-34** — Each run gets a fresh runner with a fresh filesystem. Nothing survives from one review to the next, so there are no leftovers to distrust or clear.

## The Agent

- **TR-35** — The agent's access to the checkout goes through a DeepAgents backend. Filesystem operations and shell execution both come from that one object, so the compute target is a single swappable dependency.
- **TR-36** — Coral uses `LocalShellBackend`, rooted at the checkout, behind the wrapper TR-52 describes. It provides the `execute` tool that satisfies FR-17 and FR-18, and its filesystem operations run as direct Python rather than as shelled-out scripts, which matters for an agent that reads and greps heavily against the budget TR-49 sets.
- **TR-37** — Nothing outside the backend may shell out into the checkout, and no other code path may hold a second notion of where the checkout lives.
- **TR-38** — Coral's own Python environment does not reach the agent's shell. `uv sync --frozen` installs Coral's dependencies into a virtualenv outside the workspace, and `VIRTUAL_ENV`, `UV_*`, and Coral's entry on `PATH` are removed from the environment the backend passes to commands, alongside the secrets in TR-10. Without this the repository's own `pytest` runs against Coral's interpreter and Coral's packages, and FR-18 breaks first and most often on exactly the Python repositories Coral is most likely to be tried on.
- **TR-39** — The agent returns a structured review object, not prose, using the `response_format` parameter on `create_deep_agent`. It carries a summary and a list of findings. Each finding carries its text and its anchor: a span of lines in a file, a single line in a file, a whole file, or the pull request as a whole. The last two share one posting path and differ only in whether a file is named, per TR-45. The object also carries a flag saying whether an empty finding list means there was nothing to find or means everything Coral would have said is already on the pull request and still stands, because FR-29 needs those told apart and only the agent knows which it is. This schema is the contract between the agent and the posting code, and per TR-9 it is the only thing the agent hands back.
- **TR-40** — The provider list on `ChatOpenRouter` is pinned to providers whose tool calling has been tested, through the `openrouter_provider` kwarg. Roughly thirty providers serve this model, OpenRouter fails over between them automatically, and tool-calling fidelity varies. An unpinned failover midway through a review looks like the agent silently getting worse. The pin is against a model alias that moves on its own schedule (TR-7), so the tested list has to be rechecked whenever the alias resolves somewhere new, and a pinned provider that stops serving the model is a hard failure rather than a quiet degradation.
- **TR-41** — `create_deep_agent` installs a summarization middleware by default, so a long review has its own context compacted while it runs. FR-13 asks for the whole change to be covered, and that promise is only as good as what survives compaction. This is a reason to keep TR-28 and TR-31 tight rather than a thing to switch off.

## Posting The Review

- **TR-42** — Findings are posted as a single GitHub pull request review. The summary becomes the review body and the anchored findings become its comments, in one API call. The review is left as a comment, never approving and never requesting changes, per FR-30.
- **TR-43** — The anchors are checked against the diff of the two commits pinned in TR-25, which is the same diff the agent saw. It is computed from the two commits rather than from the working tree, because FR-19 lets the agent write scratch files into that tree, and it is not refetched from GitHub at posting time, because by then either branch may have moved and the check would be against a change Coral did not review.
- **TR-44** — GitHub accepts a review comment only on a line that is part of the diff. Findings whose anchor falls outside it are moved into the summary with their intended file and line named, which is what satisfies FR-24. This is expected to fire regularly rather than being an edge case.
- **TR-45** — A whole-file finding goes into the summary by construction rather than by failure. The `comments` array on the create-review endpoint accepts only `path`, `position`, `body`, `line`, `side`, `start_line`, and `start_side`, so the `subject_type` that marks a file-level comment has nowhere to go in a batched review. Posting one would mean a second API call per finding, which FR-25 rules out.
- **TR-46** — GitHub accepts or rejects a review as a whole, so one bad anchor costs every finding in it. The pre-check in TR-44 cannot be sufficient on its own, because GitHub decides what is inside the diff using its own patch generation rather than the workflow's, and because the base branch may have moved since TR-25 pinned it. A rejected call is therefore retried, and the retry is unconditional in its effect: every anchored finding is demoted into the summary and the review is posted again with no inline comments at all. Demoting only the anchors GitHub named would be better for the reader and is worth doing when the 422 response identifies them, but it cannot be the mechanism, because a retry that depends on the error naming the offending entry fails silently when it does not. The guarantee FR-24 asks for is that no finding is lost, and a summary-only repost delivers it whatever the error body says.
- **TR-47** — The review names the commit it reviewed, in the API call and not only in the prose. Naming it is what puts each comment on the line the agent meant, since GitHub resolves a comment's position relative to a commit. It is also what lets GitHub mark that comment outdated later, when a further push changes the code underneath it, and what makes the record TR-29 reads back.
- **TR-48** — The workflow rechecks the pull request's state immediately before posting, per FR-34. The check in TR-26 was minutes ago, and the whole point of FR-34 is not to post advice onto something already merged.

## Time Budget

- **TR-49** — Coral owns its deadline. The budget is 20 minutes, measured from the start of the review step, with enough headroom left over to post a review afterwards, which means the review step is always still running when its own deadline fires. Everything under "Failure" below depends on this. The number is chosen rather than measured.
- **TR-50** — The job's `timeout-minutes` is 30, and it is a backstop and never the mechanism. A job cancelled by GitHub cannot post the failure comment FR-31 promises, so Coral's own deadline is set comfortably inside it and is what actually fires. The gap covers resolve, checkout, dependency installation, and posting, and leaves several minutes spare.
- **TR-51** — The deadline needs a mechanism, because wanting one does not produce one. It takes all four of: a step cap on the agent loop, set to 200 and applied by overriding the `recursion_limit` on the compiled graph, since DeepAgents sets that to 9,999 and 9,999 is not a limit; an elapsed-time check between steps that ends the run when the budget is spent; a request timeout on the model call, set to 180 seconds so a hung connection cannot outlast the budget, and passed in milliseconds because `ChatOpenRouter` takes `timeout` in milliseconds; and the bounded shell timeout in TR-52. All three numbers are chosen rather than measured.
- **TR-52** — The per-command shell timeout is capped at 300 seconds by a wrapper around the backend, which clamps the `timeout` argument before delegating to `LocalShellBackend.execute`. The wrapper is the mechanism, and it has to be, because neither of the two obvious alternatives caps anything. `LocalShellBackend(timeout=...)` sets only the default used when the model omits the argument. The ceiling on what the model may ask for is `max_execute_timeout` on `FilesystemMiddleware`, which defaults to 3,600 seconds, and `create_deep_agent` constructs that middleware itself and neither accepts nor forwards the parameter. Uncapped, a model that decides a slow test deserves an hour gets an hour, and the elapsed-time check in TR-51 does not run until the command returns.
- **TR-53** — A pull request costs one full agent run for its automatic review and one more every time somebody asks, because FR-13 reviews the whole change each time rather than only what is new. Nothing automatic multiplies that, which is the point of FR-4. A run is paid for whether or not it produced anything: an agent that spends its budget failing to install the repository's dependencies costs the same as one that finds five bugs. On a private repository those minutes are billed, so the cost of Coral is the number of pull requests opened multiplied by the length of a run.

## Failure

- **TR-54** — The review step reports its own failures. Because Coral owns the deadline (TR-49), a step that runs out of time or throws is still running, still holds the checkout, and is still the deterministic code that posts to GitHub. It posts the failure comment itself, immediately. Per FR-36 the comment carries the reason and nothing else, and the partly built review object is dropped. Before returning, the step writes a marker into the runner's temporary directory recording that the failure has been reported.
- **TR-55** — A final report step, conditioned on the job having failed, posts the failure comment for everything the review step could not. Resolve can fail on a rate-limited API call or a missing secret, the checkout can fail on a force-pushed SHA or a full disk, and dependency installation can fail on its own. None of those reach the review step, and all of them leave a person who has already seen Coral's reaction under FR-9 waiting for a review that will never arrive. The step skips when TR-54's marker is present, so a failure is reported once. This is what makes FR-31 true for every failure rather than only for the ones the agent produces.
- **TR-56** — A run that dies in a way no step can report — the runner itself vanishing, or the job being cancelled by GitHub's own timeout — is visible as a failed run in the repository's Actions tab, with its logs. Nothing else has to watch for it, and the recovery is that a person asks again, which FR-35 keeps possible.

## Runner Limits

- **TR-57** — A standard GitHub-hosted Ubuntu runner gives 4 vCPU and 16 GB of RAM on a public repository, and 2 vCPU and 8 GB of RAM on a private one. Both give 14 GB of SSD. Larger runners are available to organizations on Team and Enterprise Cloud plans.
- **TR-58** — Submodules are not initialized and Git LFS pointers are not resolved. Both are a single input on the checkout, so this is a default rather than a limit.
- **TR-59** — Coral runs directly on the runner and never inside a container of its own. This is what makes FR-18 possible at all. A container action would hand the agent Coral's image, which knows nothing about the repository under review, and running that repository's tests needs that repository's toolchain. GitHub's hosted runner images carry a broad preinstalled toolchain, and inheriting it is the only reason Coral can run a test in a repository it has never seen. The cost is that Coral's own dependencies are installed beside the repository's, which TR-38 keeps out of the way.
- **TR-60** — The workflow file on the comment paths is always read from the default branch, so a pull request cannot change how it is reviewed by asking. On the `pull_request` path the file comes from the pull request's own head, so a pull request can change the workflow that reviews it — disable Coral, alter its prompt, widen the `permissions` block, or read the OpenRouter key. That population is people with write access, running code on a runner that already holds the repository's secrets, so it is the same trust every other job in the repository is given. It is recorded because it is not obvious.

## Secrets And Configuration

- **TR-61** — Coral needs one secret: an OpenRouter API key, supplied to the reusable workflow by the repository that calls it. The GitHub token comes from the job (TR-11), so there is nothing else to store.

## Undecided

Decisions arrive here before they are made, not after.

- **Whether `pull-requests: write` covers the endpoints Coral needs in the issues namespace.** The reaction in TR-23 and the failure comment in TR-54 both go through `/repos/{owner}/{repo}/issues/...`, and GitHub's reference does not state the fine-grained permission for those endpoints. If it turns out `issues: write` is required, TR-11 grows by one line. This is worth testing before anything else is built, because it fails on the first run.
- **The numbers.** TR-28's conversation bound, TR-31's size backstop, TR-49's deadline, TR-50's job timeout, TR-51's step cap and request timeout, and TR-52's shell cap are all chosen rather than measured. They are stated so the design is complete and testable, not because any of them is known to be right. The first real review against a real repository is what settles them.
- **Whether GitHub's 422 identifies the offending anchor.** TR-46 does not depend on it and is correct either way. If the error body does name the bad entries, the retry can demote only those and keep the rest inline, which is strictly better for the reader.
